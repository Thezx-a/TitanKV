总览/客户端层

Client Layer · 三种接入方式

客户端层提供三种接入：Next.js 控制台（人类）、Cobra CLI（运维/脚本）、Go SDK（机器对机器）。 三者最终都打 Gateway 的 :8080，鉴权方式各异。

Next.js 控制台 Cobra CLI · keyforge Go SDK titan JWT / APIKey SSE scan

接入流程 · 三种客户端如何抵达 Gateway

1

Web 控制台 · 登录写 cookie web/

用户在 /login 提交账密 → Auth 微服务验证 → 返回 Access + Refresh；前端写 titan_token cookie（httpOnly + SameSite=Strict）。

崩溃点 A：登录成功但 cookie 写失败（浏览器拦截）→ 用户重定向回登录页；可换成 sessionStorage 暂存。

2

apiFetch · 自动注入 Bearer web/lib/api.ts

所有 fetch 走 apiFetch，自动读 cookie 注入 Authorization: Bearer，401 时尝试 Refresh。

崩溃点 B：Access 过期且 Refresh 也过期 → 401 拦截重定向登录页，重新建立认证态。

3

CLI · keyforge addAuth client-cli/main.go

addAuth() 注入 Authorization: Bearer $TITANKV_TOKEN 或 --token；token 从环境变量或参数取。

崩溃点 C：token 失效 → 401，CLI 报错退出；脚本侧需主动调 Login 续签。

4

SDK · New + Login client-go/titan/client.go

传入 gatewayURL + apiKey 构造 Client；apiKey 为空时调 Login(user, pass) 拿 JWT，缓存到 c.token。

崩溃点 D：JWT 过期但 Client 未感知 → 服务端 401；SDK 内置 maxRetries 自动重试 Login。

5

HTTP 请求 · 抵达 Gateway:8080 L3

所有客户端最终都打 Gateway :8080，进入洋葱中间件链（RequestID → Auth → RBAC → ... → 反向代理）。

崩溃点 E：Gateway 不可达 → 客户端 connection refused；CLI/SDK 重试机制兜底，Web 给用户提示。

6

Scan SSE · 流式响应直读 CLI

keyforge scan 用 io.Copy(os.Stdout, resp.Body) 把 SSE 流直接打到 stdout，无需等待全量。

崩溃点 F：流中途连接断 → io.Copy 返回 EOF + 错误，已读数据已输出；用户重试即可（scan 是幂等读）。

核心组件知识点

keyforge CLI · Cobra 命令行

client-cli/main.go

用 spf13/cobra 实现的 KV 操作命令行工具，名叫 keyforge，通过 Gateway 调用。

  • 子命令：ping 健康检查、put <key> <value>、get <key>、scan --start --end（SSE 流式）。
  • 持久参数：--url（默认 http://127.0.0.1:8080，环境 TITANKV_URL）、--token（环境 TITANKV_TOKEN）。
  • 鉴权：addAuth() 注入 Authorization: Bearer <token>。
  • scan SSE：io.Copy(os.Stdout, resp.Body) 直接把流式响应打到标准输出。
  • 错误处理：resp.StatusCode >= 400 时返回 HTTP %d。
# ping
keyforge ping --url http://localhost:8080

# put (需 token)
keyforge put foo bar --token $TITANKV_TOKEN

# 流式 scan
keyforge scan --start a --end z --token $TITANKV_TOKEN

Go SDK · titan.Client

client-go/titan/client.go · types.go · errors.go

面向程序集成的 Go 客户端，支持 APIKey（机器对机器）或 JWT Login 两种鉴权，内置重试。

  • Client 结构：gatewayURL / apiKey / http / maxRetries。
  • Option 模式：WithMaxRetries(n)（默认 3）、WithHTTPClient(h)（自定义代理/超时）。
  • New(gatewayURL, apiKey, opts...)：apiKey 为空时用 JWT，单独调 Login。
  • 默认超时：10s。
  • API：Login / Put / Get / Delete / Scan 等。
  • 错误：errors.go 定义结构化错误类型。
  • 类型：types.go 定义 LoginResponse 等数据结构。

设计深度分析

客户端层是用户接触系统的第一层，其设计取舍直接决定体验与安全。本节覆盖崩溃恢复、JWT vs APIKey、SSE 流式、CLI vs SDK vs Web、SDK 重试策略等核心议题。

1. 崩溃恢复 · 六种客户端场景

CASE A登录后 cookie 写入失败

浏览器策略拦截或 SameSite 不匹配，cookie 未落盘。Web 用户感知到登录循环；可改用 sessionStorage + Authorization header 双轨。

语义：无损 · 仅体验降级
CASE BAccess/Refresh 双过期

Access 30min + Refresh 7d 都过期，需重新登录。Web 端 401 拦截自动重定向登录页。

语义：可恢复 · 用户重新认证
CASE CCLI token 失效

运维脚本长期未跑，JWT 过期。CLI 报 401 退出；脚本侧需主动调 Login 续签或用 APIKey 替代。

语义：脚本中断 · 推荐改用 APIKey
CASE DSDK JWT 过期

Client 未感知 token 过期，服务端 401；SDK 内置 maxRetries 自动重试 Login，用户无感。

语义：可恢复 · SDK 自动续签
CASE EGateway 不可达

网关进程崩 / 网络分区，connection refused。CLI/SDK 重试 + 退避；Web 给用户提示并禁用按钮。

语义：服务中断 · 客户端兜底
CASE FSSE 流中途断

scan 流式响应中途连接断，io.Copy 返回 EOF+错误，已读数据已输出。用户重试即可（scan 幂等读）。

语义：可重试 · 部分结果已落地

2. JWT vs APIKey · 为什么提供两种

维度JWT (Access)APIKey
典型客户端 Web / CLI / SDK(Login) SDK (机器对机器)
有效期 30min，需 Refresh 长期，按需吊销
验证方式 本地 HMAC 验签，无 DB 查询 查 Redis / DB 看 jti 黑名单
吊销能力 jti 黑名单（Redis） 直接删 DB 行，立即生效
权限范围 含 role / user_id scope 字段精细控制
安全风险 泄露 30min 窗口 泄露窗口大，需 IP 白名单

结论：JWT 优化人类场景（短时窗 + Refresh 续航），APIKey 优化机器场景（长期 + 精细 scope）。两种共存让 Web/CLI/SDK 各取所需，不要强行统一。

3. CLI (Cobra) vs SDK (Go) vs Web (Next.js) · 三客户端的取舍

维度Cobra CLIGo SDKNext.js Web
用户 运维 / 脚本 程序集成 人类
交互 命令行参数 + stdin/stdout API 调用 + 类型安全 表单 + 可视化
鉴权 --token / env APIKey 或 JWT Login cookie + 自动 Refresh
流式输出 io.Copy stdout，最简 chan / callback SSE EventSource
错误处理 exit code + stderr typed errors toast + 重试
实现成本 ~300 行单文件 ~500 行多文件 整个 Next.js 工程

三种并存的优点

  • 覆盖人类 / 运维 / 程序三种使用场景
  • CLI 是最低成本的调试工具
  • SDK 提供类型安全，便于二次开发
  • Web 给非技术用户提供可视化

缺点

  • 三种客户端都要维护，迭代成本×3
  • 鉴权逻辑三套实现（cookie/token/apikey）
  • 错误码映射三套（exit code / typed err / toast）

优化方向：① 抽取 client-core 公共库（鉴权 + 重试 + 错误类型），CLI/SDK 都基于它构建；② 用 OpenAPI spec 自动生成 SDK，减少手写成本；③ Web 端用 TanStack Query 统一错误展示。

4. SSE 流式 scan · 为什么不用 WebSocket / gRPC stream

维度SSE (本项目)WebSocketgRPC stream
协议 HTTP/1.1，单向服务端推 双工，需 Upgrade 握手 HTTP/2，需 proto + 客户端 stub
实现 服务端 Flusher，客户端 EventSource gorilla/websocket，需读 + 写循环 proto + grpc-go，复杂
代理友好 普通 HTTP，Nginx/网关透传 需 Upgrade，部分代理不支持 HTTP/2，部分 LB 不支持
CLI 输出 io.Copy stdout，最简 需解析 frame 需 proto decode
双向通信 单向（仅服务端→客户端） 双向 双向

结论：scan 是单向流式输出场景，SSE 协议简单、代理友好、CLI 实现成本最低。双向通信才需 WebSocket/gRPC stream。

5. SDK 重试策略 · maxRetries=3 的取舍

SDK 默认 WithMaxRetries(3)，覆盖网络瞬时故障；但重试会放大写请求，需配合幂等性。

重试的优点

  • 瞬时网络抖动对用户无感
  • JWT 过期可触发自动 Login 续签
  • 降低运维告警噪音

重试的代价

  • 非幂等写（如转账）重复执行风险
  • 放大流量，雪崩风险
  • 无退避策略时持续打挂的服务

优化方向：① 区分幂等：GET/DELETE/PUT（带版本号）可重试，POST 用 Idempotency-Key；② 指数退避 + jitter：1s/2s/4s + 随机偏移，避免同步重试雪崩；③ 熔断器：连续失败 N 次后短路一段时间，让上游恢复。

6. cookie httpOnly + SameSite=Strict · 为什么这样配置

配置httpOnly + SameSite=Strict普通 cookie
XSS 偷 token JS 读不到，无法窃取 document.cookie 可读
CSRF 攻击 跨站不带 cookie 跨站自动带，需 CSRF token
第三方嵌入 无法跨站嵌入 可跨站（如 OAuth 回调）
体验 从外部链接进入需重新登录 无缝

结论：本项目是 KV 服务，无第三方嵌入需求，Strict 最安全。需 OAuth 回调场景可降级 SameSite=Lax。

7. 总体优缺点与优化路线

当前设计优点

  • 三客户端覆盖完整使用场景
  • JWT + APIKey 双轨鉴权，按场景选最优
  • SSE 流式 scan，CLI 实现极简
  • SDK 内置重试，瞬时故障无感
  • cookie httpOnly + Strict，安全默认

当前设计缺点

  • 三客户端维护成本高
  • CLI token 失效需手动续签
  • 重试无指数退避，雪崩风险
  • 无 Idempotency-Key，POST 重试不安全
  • SDK 错误类型未对接 OpenAPI 自动生成
优化路线（按优先级） P0 · 公共 client-core 库：CLI/SDK 共享鉴权 + 重试 + 错误；
P1 · OpenAPI 自动生成 SDK：多语言客户端，零手写；
P1 · 指数退避 + 熔断器：避免重试雪崩；
P2 · Idempotency-Key：POST 重试安全；
P2 · CLI token 自动续签：检测过期主动 Login；
P3 · WebSocket 双向流：未来支持订阅 / watch 场景。
为什么这个层是 L1？ L1 客户端 → L2 网络库 → L3 网关 → ... → L8 前端。客户端层在最外层，是人类/程序接触系统的入口。它的关键约束是：不知道底层架构（以为就是单机 HTTP），但需把鉴权、重试、错误处理这些"客户端关切"做扎实。详见 网关设计分析 与 前端控制台设计分析。
