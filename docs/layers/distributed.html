总览/分布式层

Distributed · Raft 共识与分片

基于 hashicorp/raft 的教学型单节点集群，验证 Raft 三个核心抽象： Apply / Snapshot / Restore。多节点复制与一致性哈希分片为后续规划。

hashicorp/raft KVFSM Apply 真理源 Snapshot/Restore WriteForwarder JoinCluster 演示 gateway/shard.go

Raft 核心三件套

Raft 用 FSM（有限状态机）抽象让副本间状态一致：所有写都通过 Apply(log) 顺序执行，Snapshot 截断日志，Restore 重建状态。

1

Client 提交写请求 http.go

客户端调用 /raft/put，HTTP handler 把 {op, key, value} 编码成 raft.Log 载荷。

崩溃点 A：请求未到达 leader → 客户端超时重试；集群无状态变更。

2

raft.Apply(Log) raft

leader 把 Log 复制到半数副本后 commit，再回调 KVFSM.Apply(l *raft.Log)。

崩溃点 B：leader 复制到一半崩溃 → 未 commit 的 Log 在新 leader 任期被覆盖；客户端感知超时后重试（Raft 不保证 exactly-once，需上层去重）。

3

KVFSM.Apply · decodeCommand → applyLocal fsm.go

opPut 写 f.data[key]=value，opDelete 删除。Apply 必须确定性：所有副本按相同顺序执行同一条 Log，最终状态一致。

崩溃点 C：Apply 中途进程崩 → 重启后 raft 重放未 Snapshot 的 Log，FSM 重新 Apply 到一致状态。Apply 函数本身必须幂等（map 写入天然幂等）。

4

真理源 · in-memory map[key] = value fsm.go

所有副本的 map 在 Apply 后最终一致。读操作直接读本地 map，不走 Raft——读不要求强一致（最终一致即足够）。

崩溃点 D：map 在内存中进程崩就丢失，但 raft 日志在磁盘；重启走 Restore 重建。

5

WriteForwarder.Put · best-effort 镜像 minikv_forward.go

异步、非阻塞把写入转发到 MiniKV，作为 LSM-Tree 持久层。关键约束：转发失败绝不能让 Apply 失败——外部 IO 是非确定性的，会让副本发散。

崩溃点 E：MiniKV 写失败 → map 已更新但 LSM 未同步；重启后从 raft 重建真理源，MiniKV 演进到最终一致（或在读路径回退到 FSM）。

6

Snapshot() · Persist(sink) fsm.go

raft 定期调 Snapshot，FSM 读锁克隆整个 map → JSON 编码写入 raftSnapshotSink，截断已 Apply 的旧 Log。

崩溃点 F：Persist 写到一半崩 → sink.Cancel()，raft 下次重试 Snapshot；不会污染状态。

7

Restore(rc) · 重启 / 新副本追赶 fsm.go

进程重启或新副本加入时，raft 先 Restore 最近的 snapshot，再重放 snapshot 之后的 Log。FSM 的 Restore 用 JSON 解码后整体替换 f.data。

崩溃点 G：snapshot 文件损坏 → raft 拒绝启动；需运维介入或回退更早 snapshot。

核心组件知识点

KVFSM · 内存 map 状态机

distributed/fsm.go

实现 raft.FSM 接口，把 Raft 日志应用到内存 map，是集群的唯一真理源。

  • Apply(l *raft.Log)：decodeCommand 解码 → applyLocal。opPut 写 map，opDelete 删 map。
  • WriteForwarder：可选，best-effort 把 Put/Delete 镜像到 MiniKV。不能让 Apply 失败（外部 IO 是非确定性的，会让副本不一致）。
  • Get(key)：直接读本地 map，不走 Raft——读不要求一致性共识。
  • Snapshot()：读锁克隆整个 map → 返回 kvSnapshot，Persist(sink) 用 JSON 编码写入 raft sink。
  • Restore(rc)：JSON 解码 → 替换 f.data，用于新副本追赶 leader 或重启恢复。
  • 错误处理：Persist 失败时 sink.Cancel()，让 raft 重试。

distributed/command.go

command 是序列化进 Raft Log 的载荷：{Op: opPut|opDelete, Key, Value}。decodeCommand 反序列化给 Apply。

设计深度分析

本节聚焦 Raft 共识子系统在崩溃恢复、技术选型、并发约束等方面的取舍——为什么这样设计，好处与代价是什么，未来怎么优化。

1. 崩溃恢复 · 七种场景与 Raft 不变量

Raft 的核心承诺是 "已 commit 的 Log 不会被覆盖" 与 "已 Apply 的状态可重放重建"。下面用七个崩溃点逐一对照该承诺。

CASE A客户端请求未达 leader

网络分区或 leader 不可达，请求超时。Raft 无任何状态变更；客户端幂等重试即可。

语义：无损 · 仅客户端体验降级
CASE Bleader 复制到一半崩溃

未达多数复制 → Log 未 commit。新 leader 选出后会丢弃前任未 commit 的 Log（term 比较 + log 匹配属性）。客户端重试可能产生重复写入。

语义：强一致未破坏 · 但非幂等操作需上层去重
CASE CApply 中途进程崩

重启后 raft 重放未 Snapshot 的 Log，FSM 的 map 写入天然幂等，状态最终一致。前提：Apply 必须确定性，不能引入外部 IO 或随机性。

语义：可恢复 · 依赖 Apply 幂等性
CASE D内存 map 丢失

进程崩 → map 清空，但 raft Log + snapshot 在磁盘持久化。重启先 Restore snapshot 再重放后续 Log，状态完整重建。

语义：可恢复 · 落盘是真理源的真正后盾
CASE EWriteForwarder 转发 MiniKV 失败

FSM map 已更新，LSM 未同步。不能让 Apply 失败，否则副本发散。MiniKV 最终一致；读路径必要时回退到 FSM。

语义：FSM 是真理源 · MiniKV 仅做加速读
CASE FSnapshot 写盘中途崩

Persist 失败 → sink.Cancel()，raft 不认这次 Snapshot，下次重新触发。旧 Log 不截断，无任何状态污染。

语义：原子性靠 sink 抽象保证
CASE Gsnapshot 文件损坏

raft 启动加载失败 → 拒绝启动。需运维介入或回退到更早 snapshot（hashicorp/raft 不自动回退多版本）。

语义：需外部备份 · 单文件是单点
为什么这样设计？ 核心权衡：Raft 把"状态变更"序列化为"日志条目"，让副本间只复制一个不可变序列，再各自 Apply。崩溃恢复因此变成"重放确定性序列"这一件事，复杂度从"分布式状态协调"降到"日志回放"。代价是：所有写都过 leader、Apply 必须确定性、读不强一致。

2. Raft vs Paxos · 为什么选 Raft

维度RaftPaxos (Multi-Paxos)
理解成本 强 leader + term 编号，状态机清晰 提议者/接受者/学习者三角色，prepare+accept 两阶段
工程实现 hashicorp/raft / etcd-raft 开箱即用，~3k 行核心 工业实现少，Spanner/Chubby 内部不公开
日志结构 顺序追加，成员变更有标准 Joint Consensus 无统一日志模型，需上层自定义
异常路径 leader election + log catch-up + snapshot 都有规范 异常路径多靠实现者自己定义
性能 leader 是瓶颈，可优化 Multi-Raft 可多 proposer 并行，理论吞吐略高
教学价值 论文带图，状态转换可数 论文数学化，难讲清

结论：本项目是教学型 + 单节点起步，Raft 的可读性和成熟库让 FSM 三件套能被快速验证。Paxos 理论更通用但实现门槛高，不适合单人项目。

3. 内存 FSM map vs 持久化 KV 状态机 · 为什么用内存 map

维度内存 map (本项目)持久化 KV (etcd 模式)
Apply 实现 m[k]=v，零 IO，<10ns 每次 Apply 一次 LSM/BBTree 写入，ms 级
Snapshot JSON 编码整个 map，简单 需触发 flush / compaction，复杂
Restore JSON 解码整体替换 逐条回放或 reload 整树
重启速度 Restore snapshot + 重放有限 Log 状态机本身已落盘，重启快但 Apply 一直慢
容量上限 受内存限制，TB 级不可行 受磁盘限制，可扩到 PB
真理源责任 FSM 即真理源，MiniKV 仅镜像 状态机即持久层，无双重真理源问题

优点

  • 实现简单：FSM 不依赖磁盘 IO，Apply 不阻塞共识
  • Snapshot 用 JSON 易读，调试方便
  • 教学价值最大化：FSM 三件套逻辑清晰可观察

缺点

  • 双重真理源：FSM map 与 MiniKV LSM 并存，需 WriteForwarder 软同步
  • 容量受限于单机内存
  • 读最终一致，不能扛跨副本强一致读

优化方向：① 状态机直接落盘（BoltDB 模式，etcd 的做法），消除 WriteForwarder 双写；② 引入 ReadIndex / Lease Read 提供线性一致读；③ 大数据量下改用增量 Snapshot（差量 + SST 复制）替代整 map JSON。

4. 为什么 WriteForwarder 必须 best-effort · 共识的确定性铁律

若让 MiniKV 写失败回滚 Apply，会触发副本发散：副本 A 的 MiniKV 写成功 → Apply 返回 ok；副本 B 的 MiniKV 写失败 → Apply 返回 err。raft 看到 A/B Apply 同一条 Log 的结果不一致，状态机崩坏。

best-effort 的好处

  • 保留 Apply 的确定性（同一 Log 在所有副本产生相同 map 状态）
  • 外部 IO 失败不污染共识层
  • FSM 仍是真理源，重启从 raft 重建

代价

  • MiniKV 与 FSM 短期不一致（最终一致）
  • 读路径需处理 fallback：FSM → MiniKV
  • 需引入对账任务定期校验两者差量

优化方向：把 MiniKV 写入从"Apply 后异步"改成"Apply 内同步但只更新 LSM 的 WAL 阶段"（写 WAL 快、ms 级），崩溃恢复时 FSM 重放 → MiniKV WAL replay，两者状态对齐。

5. Snapshot 策略 · 全量 JSON vs 增量 SST

维度全量 JSON map (本项目)增量 SST (RocksDB/etcd 模式)
实现复杂度 ~30 行，json.Marshal 需在 FSM 内实现层级的 SST 文件追踪与差量序列化
大状态表现 map 越大 Snapshot 越慢，1GB 起就明显 只复制变化层，GB 级仍快
Restore 速度 JSON 解码全量，慢 直接 mmap SST 文件，秒级
存储空间 每次 Snapshot 完整副本 Level 元数据共享文件，省空间
调试友好 snapshot 是可读 JSON 需 SST dump 工具

结论：教学场景下 map < 100MB 时全量 JSON 足够；生产场景必须改增量 SST。RocksDB Checkpoint 接口是最成熟的增量 snapshot 实现参考。

6. 单节点 Bootstrap vs 多 voter 集群 · 教学梯度

阶段 11-node Bootstrap

单节点自举为 leader，验证 FSM Apply/Snapshot/Restore 三件套工作正常，无复制复杂性。

已实现 · 核心抽象可信
阶段 2JoinCluster 多 voter 演示

通过 raft.AddVoter 把 follower 加入集群，验证 leader 复制 + 半数 commit 路径，但仍是同机多实例。

演示性 · 真实多机需网络与运维
阶段 3多机生产集群 (planned)

跨机 leader/follower、节点发现、自动 rebalance、跨片事务 —— 尚未实现，是后续规划。

未做 · 简历可不写 Raft 生产能力
阶段 4一致性哈希分片 (planned)

distributed/shard 与 skynet ConsistentHashLB 联动，把 key 分散到多 raft 组，每个组独立选主。

规划 · 与 L2 负载均衡联动

为什么渐进式实现：Raft 共识算法实现复杂，单节点先把 FSM 三件套抽象稳了，再加多机；分片放在最后是因为它依赖前两者的稳定性。一步到位多机分片会让调试难度指数级上升。

7. Raft 日志 vs Redis AOF · 都是日志，差在哪

维度Raft LogRedis AOF
复制语义 多数 commit 才算成功，强一致 异步复制到副本，最终一致
leader 角色 强 leader，所有写必经 主从弱 leader，可读写分离
故障切换 自动选主，term + 投票 Sentinel / Cluster 模式，配置复杂
性能 多副本 RTT 拖累，写 ~1ms 单机内存写，<100us
一致性保证 已 commit Log 不丢 fsync 策略决定，可能丢 1s 数据

结论：Redis AOF 优化"快"，Raft 优化"强一致"。本项目用 Raft 做 map 真理源（量小、一致性高），用 MiniKV LSM 做热数据存储（量大、最终一致）—— 二者互补。

8. hashicorp/raft vs etcd-raft · 库选型

维度hashicorp/raft (本项目)etcd-raft
API 易用 FSM 接口 3 个方法，~50 行起步 需实现 RaftReady 全套回调，~500 行
传输层 自带 TCP transport，开箱即用 需自行实现 RaftTransport，集成 gRPC
Multi-Raft 无原生支持 原生 Multi-Raft，分片友好
生产成熟度 Consul/Vault/Nomad 用，稳 etcd/K8s 用，承载大规模生产
性能 中等，单 Raft 组上限 ~10k QPS 高，Multi-Raft + Batch 可百万 QPS

结论：教学场景 hashicorp/raft 上手快；etcd-raft 适合追求极致性能与多组分片的生产实现。本项目未来若做多组分片，可平滑迁移到 etcd-raft。

9. 总体优缺点与优化路线

当前设计优点

  • FSM 三件套清晰可验证，状态机抽象纯洁
  • Apply 不做 IO，共识层延迟低、实现稳
  • Snapshot 用 JSON 易调试、可读
  • WriteForwarder 边界明确：FSM 是真理源，MiniKV 是镜像
  • hashicorp/raft 库稳定，文档丰富

当前设计缺点

  • 单节点 Raft 共识没复制，只是验证抽象
  • 全量 JSON Snapshot 大状态时不可用
  • 双重真理源（map + MiniKV）增加读路径复杂度
  • 读最终一致，不抗跨副本强一致读
  • 无 Multi-Raft，分片方案未落地
优化路线（按优先级） P0 · 多机三节点集群：真正验证半数复制、leader 切换、follower 追赶；
P1 · ReadIndex 线性一致读：读前向 leader 确认 lease，提供强一致读；
P1 · 增量 SST Snapshot：替换 JSON 全量，参考 RocksDB Checkpoint；
P2 · 状态机落盘：消除 WriteForwarder 双写，FSM 直接驱动 BoltDB；
P3 · Multi-Raft 分片：迁移到 etcd-raft，与 L2 一致性哈希联动；
P3 · 跨片事务：Percolator 模型或两阶段提交。
为什么这个层是 L5？ L3 网关 → L4 微服务 → L5 分布式 Raft → L6 存储。Raft 层在微服务和存储之间：上层调用 raft.Apply 写入共识，下层把共识真理源镜像到 MiniKV LSM。这样上层接口简单（不知道底层存储），下层存储可换（不知道上层业务），Raft 充当了"一致性仲裁者"。详见 请求链路 与 存储引擎设计分析。
