总览/存储引擎层

MiniKV · LSM-Tree 存储引擎

C++17 从零实现的 LSM-Tree 存储引擎，参考 LevelDB / RocksDB 的公开资料。 一条 db.Put() 写入 WAL、落到 MemTable（`shared_ptr` 锁外读）（跳表）、刷盘成 SSTable、被 Compaction 合并—— 这条链路上每个组件都在 minikv/src/core/ 里。

C++17 WAL SkipList SSTable Compaction MVCC BloomFilter 主从 Reactor

整体写入 / 读取流程

LSM-Tree 的核心是「写优化、读放大」：写入只追加到内存与 WAL，读取需要合并多个层级。下面把写路径与读路径并排竖向展开。

写路径 · Put / Write

1

DBImpl::put / write

取 write_mutex_，组队 Group Commit。

2

WAL::append + fsync

leader 批量追加日志并 fsync（≤32 条 / 500μs 超时）。

崩溃点 A：fsync 返回前崩溃 → 这批写入丢失但一致。

3

MemTable::put (SkipList)

写锁下插入跳表，seq 递增，InternalKey 编码。

4

maybeFlush

mem_usage 超阈值 → swap memtable_ → 旧表入 immutable_list_ → push flush_queue_。

关键：写路径只做轻量 swap，不等 SSTable 构建。

5

flush_thread_ 后台刷盘

SkipList 扫描 → SSTableBuilder::finish → Version::addLevelFile(L0) → unlink 旧 WAL。

崩溃点 B：SSTable 写一半崩溃 → 恢复时检测 magic/footer 不符，丢弃半成品。

读路径 · Get

1

DBImpl::get

在 write_mutex_ 下快照 memtable_ + immutable_list_。

2

memtable_->get

最新写入，跳表查找 O(log n)。

3

immutable_list_ 遍历

冻结中待刷盘的 MemTable，FIFO 顺序查找。

4

L0 SSTable（时间倒序）

BloomFilter 先 mightContain 过滤，命中再读 Block。

5

L1..Ln SSTable + BlockCache

层级查找，BlockCache 命中优先；返回最新 seq 的可见版本。

核心组件知识点

WAL · Write-Ahead Log

minikv/src/core/wal.cpp · wal.h

WAL 是崩溃恢复的命脉：写入先追加到磁盘日志，再改内存，崩溃后通过回放 WAL 重建 MemTable。

  • 文件命名：wal-<N>.log，每个 MemTable 一代对应一个 WAL 文件，file_number 由 Version 单调分配。
  • Group Commit：批量 WAL + 摊销 fsync。写线程组队（kMaxGroupSize=32，超时 500μs），leader 一次性把整组写盘并 fsync，follower 等待。
  • WAL 轮转：rotateWal() 在 MemTable 冻结时切新文件，旧 WAL 在 flushOne 完成后 unlink。
  • 恢复：recover() → listWalFiles() → replayWalFile() 重放到 MemTable。
  • 垃圾回收：purgeOrphanSSTables() 清理崩溃遗留、不在 MANIFEST 中的孤儿 SST 文件。

MemTable · 跳表 SkipList

minikv/src/core/skip_list.h · memtable.cpp

MemTable 用跳表实现有序写入与快速查找，并发用读写锁（std::shared_mutex）控制。

  • 最大层数：kMaxLevel = 32，与 LevelDB 一致，保证概率层数分布合理。
  • 随机层数：randomLevel() 每层以 0.5 概率提升（std::uniform_int_distribution(0,1)），期望层高 O(log n)。
  • SkipNode 结构：key / value / forward[level+1]，forward 即各层后继指针。
  • 并发：put/del 持写锁，get/entries/approximateMemoryUsage 持读锁，读写不互斥。
  • 内存跟踪：mem_usage_ 累加 sizeof(SkipNode) + key.size() + value.size()，用于 maybeFlush() 触发阈值。
  • 比较函数：InternalKeyCompare——按 user_key 升序，相同 user_key 按 seq 降序（新版本在前）。

SSTable · 磁盘文件布局

sstable_builder.h · sstable_reader.cpp

SSTable 是不可变的有序磁盘文件，由数据块 + 索引块 + 尾部 footer 组成。

+-----------------------------+
| data block #0 .. #N         |   每块头 13 字节:
| index block                 |     crc(4) + physical_size(4)
| footer (48 bytes)          |     + uncompressed_size(4) + type(1)
+-----------------------------+

Footer 48 字节:
  8B index_offset | 8B index_size
  1B format_version(=1) | 1B reserved
  30B padding(0) | 8B magic = 0x4D4B53535441424C
  • 块大小：默认 block_size = 4096 字节，超过即 flushDataBlock()。
  • 索引块：保留 [crc][size][entries] 头部，可不解压直接解析；存储各数据块的边界 key。
  • 魔数校验：kSSTableMagic = 0x4D4B53535441424C（"MKSSTABLE"），打开时校验。
  • 版本兼容：format_version 字段区分新旧 block 头格式（legacy 8 字节 vs 新 13 字节）。
  • BloomFilter：构建时同步生成，落盘到独立文件，读时先过滤不存在的 key。

Compaction · 合并策略

minikv/src/core/compaction.cpp

Compaction 把多代 SSTable 合并去重，清理 tombstone，控制读放大。独立后台线程循环执行。

  • 触发条件：L0 文件数 >= l0_trigger_ 或 triggerCompaction() 手动触发。
  • 合并流程：mergeLevelFiles 把 src 层所有文件读入内存 → std::sort 按 InternalKey 排序 → 重建新 SST 到 dst_level。
  • 去重规则：相同 user_key 只保留最新 InternalKey（排序后第一个）；旧版本丢弃。
  • tombstone 清理：InternalKeyType == kDeletion 时跳过（仅在合并到更深一层时安全清除）。
  • 缓存失效：invalidateCache(src_files) 清理旧文件在 BlockCache 中的条目。
  • 原子提交：成功后 version_->addLevelFile(dst, newFile) + removeLevelFiles(src) + unlink 旧文件。
  • 空文件优化：若合并后 kept == 0，删除新文件并直接清空 src 层。
  • 失败重试：compaction_failures_ 计数，失败时设 triggered_=true 下轮重试。

MVCC · 多版本并发控制

minikv/src/core/internal_key.cpp

InternalKey = user_key + trailer(8 字节)。trailer 编码 seq 与 type，让多版本与删除标记在同一个有序结构中并存。

// trailer 打包
uint64_t packed = (seq << kTypeBits) | type;
// 内部键排序规则 (InternalKeyCompare)
1) user_key 升序
2) 相同 user_key → seq 降序 (新版本在前)
3) 相同 seq → type 升序
  • API：InternalKeyEncode / UserKey / Sequence / Type / Compare。
  • 异常容错：长度不足 trailer 时退化为原始字节序比较，避免越界。
  • 小端编码：utils::encodeFixed64 / decodeFixed64，跨平台一致。

BloomFilter · 布隆过滤器

minikv/src/core/bloom_filter.h · utils/hash.h

SSTable 的索引前置：读 key 前先问 BloomFilter「可能存在吗」，避免无谓的磁盘 IO。

  • 双哈希：h1 = murmurHash2(key, 0xbc9f1d34)、h2 = murmurHash2(key, 0x9e3779b9)，pos = (h1 + i*h2) % bits。
  • 误判率：默认 1%（false_positive_rate = 0.01），bits_per_key 由 -log(p) / log(2)^2 推导。
  • 哈希次数：num_hashes = bits * log(2)，钳制在 [1, 30]。
  • 持久化：persist() 写 num_hashes_ + bits_per_key_ + bits_.size() + bits_，load() 反序列化。
  • 位图操作：bits_[pos/8] |= (1 << (pos%8))，查询时全部命中才返回 true。

DBImpl · 对外接口与后台线程

minikv/src/core/db_impl.h · db_impl.cpp

DBImpl 实现对外 DB 接口，编排 WAL / MemTable / flush / Compaction 多个线程。

  • 对外 API：put / get / del / write(WriteBatch) / newIterator / compact / waitFlush。
  • 可见性契约：Get 在 write_mutex_ 下快照整个 immutable_list_，随后无锁迭代——读不被写阻塞。
  • 后台 flush：写路径只做「swap memtable → immutable, rotate WAL, push to flush_queue_」，从不等待 SSTable 构建。
  • flush 线程：flushLoop() 从 flush_queue_ FIFO 取出，flushOne() 做 SkipList 扫描 → SSTableBuilder → addLevelFile → unlink WAL。
  • 数据结构：memtable_(最新) → immutable_list_.back() → ... → front()(最旧) → L0 SSTable(时间倒序) → L1+ SSTable。
  • Group Commit 状态：group_leader_active_ 标记 leader，follower 等 group_cv_。

Manifest + Version · 元数据管理

manifest.cpp · version.cpp

Manifest 记录 SSTable 元数据变更日志，Version 是当前生效的 SSTable 集合快照。

  • Version：维护每层 SSTable 文件路径列表，提供 addLevelFile / removeLevelFiles / getLevelFiles / nextFileNumber / shouldCompactL0 / shouldCompactLevel。
  • Manifest：追加写编辑日志（add file / remove file），重启时重放重建 Version。
  • 文件号：nextFileNumber() 单调递增，WAL 与 SSTable 共用编号空间。

BlockCache + LRU + Compression

block_cache.h · utils/lru_cache.h · compression.cpp

读路径的优化三件套：块缓存降低重复读、LRU 淘汰、Snappy 压缩省盘。

  • BlockCache：按 (path, offset) 缓存解压后的 Block，invalidatePath 在 Compaction 删文件时清理。
  • LRU：utils/lru_cache.h，哈希 + 双向链表，访问即移到头部，满时淘汰尾部。
  • Compression：默认 CompressionType::kSnappy，SSTable 块写入时压缩，读时按 type 解压。

原生网络层 · 主从 Reactor

minikv/src/network/server.h · event_loop.cpp

minikv 自带一个原生 TCP 服务（非 skynet），Go Data 通过 MINIKV_ADDR 直连。

  • 主 Reactor：loop_ 只负责 accept，新连接按 round-robin 分发到 Sub Reactor。
  • Sub Reactor：io_pool_（io_threads 个 EventLoopThread）处理读写，默认 4 线程。
  • 业务线程池：biz_pool_（biz_threads 个）跑 processRequest，与 IO 解耦；biz_threads=0 时在 IO 线程内同步处理。
  • API：run() / stop() / port() / ioThreads() / bizThreads()。
  • 对比：这是 minikv 的「教学版」网络层；项目对外的 :8080 前置是 skynet（C++20 协程）。

设计深度分析

下面把 LSM-Tree 引擎的设计决策拆成三类来看：崩溃恢复（不同崩溃点 + 恢复语义）、 核心数据结构选型（跳表 vs 红黑树 / B+ 树）、整体取舍与优化路径。 每一项都给「为什么这样选 → 好处 → 缺点 → 优化方向」四段式展开。

1. 崩溃恢复 · 七种场景

LSM-Tree 的崩溃恢复依赖一个核心不变量：WAL 持久化成功的写入，恢复后必须可见；WAL 未 fsync 的写入，允许丢失但不允许半截。 写路径上有 崩溃点 A（WAL fsync 前）、崩溃点 B（SSTable 写一半）， 加上 MemTable 冻结 / Compaction 提交 / Manifest 落盘 / 启动恢复 等阶段，组合出七种典型崩溃场景：

CASE 1崩溃点 A · WAL fsync 未完成

leader 把整组写入追到 wal-<N>.log 但 fsync() 还没返回时进程崩溃。 OS page cache 中可能有部分数据，磁盘上要么全有要么全无。

为什么这么设计：Group Commit 用「批量 + 单次 fsync」摊销开销，必须接受 fsync 前崩溃的窗口期。语义是 all-or-nothing per group。

恢复语义：丢弃整组 · 数据一致
CASE 2崩溃点 A 后 · WAL fsync 完成但 MemTable 未写

fsync 返回了，但还没来得及写 MemTable 跳表就崩溃。 恢复：recover() 会 replayWalFile() 把这条记录重新写回 MemTable——这正是 WAL 的本职工作。

好处：写路径无需在 MemTable 写完后再落第二份磁盘记录，WAL = 唯一真相源。

恢复语义：WAL 回放 · 无丢失
CASE 3崩溃点 B · SSTable 写一半

flush 线程正在构建 sst-<N>.sst，写完 data block 但 footer 还没落，进程崩。 文件存在但 footer magic 不符 或 index_offset 越界。

为什么这么设计：SSTable 用 48 字节 footer + magic = 0x4D4B53535441424C（"MKSSTABLE"）做完整性闸门。打开时校验失败即丢弃。 缺点：半成品文件占用磁盘，需 purgeOrphanSSTables() 在启动时清理孤儿。

恢复语义：丢弃半成品 · WAL 仍在 → 回放重建
CASE 4MemTable 冻结后 · WAL 未 unlink

MemTable swap 进 immutable_list_，新 WAL 已切换，但旧 WAL 还没被 flushOne() 删掉就崩溃。

恢复策略：启动时 listWalFiles() 会枚举所有 wal-*.log，按 file_number 顺序回放。 旧 WAL 的内容会重建出 immutable MemTable，flush 线程继续刷盘。新 WAL 的内容重建当前 memtable_。 好处：WAL 是线性有序的，恢复逻辑简单。

恢复语义：全量回放 · 无丢失
CASE 5Compaction 提交前崩溃

Compaction 已经把 src 层文件读到内存、排好序、新 SST 写完了，但 version_->addLevelFile + removeLevelFiles + unlink 还没原子提交。

为什么这么设计：Manifest 是 编辑日志，add/remove 先写 Manifest 再改 Version 内存结构。恢复时 新 SST 在磁盘上但不在 Version 中，下次启动会被 purgeOrphanSSTables() 当孤儿清理。 缺点：浪费一次 Compaction 的 IO；优化：RocksDB 用 Current 指针原子切换 MANIFEST 快照，MiniKV 暂未实现。

恢复语义：Compaction 作废 · 浪费 IO · 一致
CASE 6Compaction unlink 旧文件后 · Manifest 未落

旧 SST 已 unlink，但 Manifest 还没追加 remove 记录就崩溃。重启后 Version 仍认为旧文件存在，读取会 open 失败。

当前实现：MiniKV 在 flushOne / Compaction 中先写 Manifest 再 unlink，避免这个窗口；但顺序仍是两个独立 syscall，理论上仍有 Manifest 写一半的风险。 优化方向：Manifest 也用「append + fsync + checkpoint」语义，并加 MANIFEST-<N> 文件号轮转。

恢复语义：理论上存在 · 实际顺序规避
CASE 7启动恢复中途崩溃

recover() 过程本身崩溃（如 replayWalFile 走到一半）。因为 WAL 是只追加，回放是幂等的（每个 entry 带 seq），二次启动可继续回放，不会重复写。

好处：恢复是 幂等 的，无需 checkpoint 即可多次重试。 缺点：大 WAL 回放慢；优化：RocksDB 在恢复到一定量后写一次 checkpoint，下次直接挂载。

恢复语义：幂等重放 · 最终一致
为什么 LSM-Tree 的崩溃恢复比 B+ 树简单？ B+ 树原地更新，崩溃后页面可能半新半旧，需要影子页 + WAL + 检查点三重保护才能保证一致。 LSM-Tree 只追加（WAL + SSTable 都不可变），崩溃点天然收敛到「正在写的那个文件」， 用 footer magic / WAL seq / Manifest 编辑日志三个闸门就能保证一致性。 代价是写放大与空间放大——但崩溃恢复的工程复杂度降了一个量级。

2. 核心数据结构 · 为什么用跳表不用红黑树

MemTable 是引擎最热的内存结构：写要 O(log n) 有序插入，读要 O(log n) 查找，flush 要有序遍历，并发读多写少。 候选有 跳表 SkipList / 红黑树 RBTree / B+ 树。下面对比并解释选型：

维度 跳表 SkipList 红黑树 RBTree B+ 树（内存版）
时间复杂度 期望 O(log n)（概率平衡） 最坏 O(log n)（强制平衡） O(log n)（节点扇出大，常数更小）
实现复杂度 ~200 行，无旋转 ~500 行，左右旋转 + 颜色翻转 ~800 行，节点分裂合并
并发友好度 无锁迭代（forward 指针只往后加） 旋转改 3 个节点，需全局写锁 分裂改父子两节点，需路径锁
范围扫描 最底层链表，O(n) 顺序遍历 中序遍历，需栈或父指针 叶子链表，原生支持
缓存局部性 节点分散，常数略大 节点分散，常数略大 节点大，cache-friendly
内存开销 每节点 forward[level] 指针（期望 1.5 个） 每节点 2 子 + 1 色 = 3 字 每节点 N 子 + 父 = 大
实现易错度 低 · 概率平衡无需维护 高 · 删除尤其复杂 中 · 分裂/合并边界
行业先例 LevelDB / RocksDB / Redis ZSET STL map / Linux CFS InnoDB / WiredTiger

选 SkipList 的好处 Pros

  • 实现简单：无旋转无重平衡，insert/find 逻辑线性，randomLevel() 是唯一随机源。
  • 并发友好：forward 指针只向后追加，旧节点不会被改；可以做到「写时复制节点 + 原子 CAS forward」的无锁读，本实现用 shared_mutex 已足够。
  • 概率平衡：不需要维护红黑性质，kMaxLevel=32 + 0.5 提升概率，期望层高 ≈ 1.5，与理论一致。
  • 范围扫描天然友好：flush 时 MemTableIterator 直接走最底层链表，O(n) 一遍扫完，与 SSTable 合并的归并迭代器无缝衔接。
  • 与 LSM 语义契合：MemTable 是短命数据结构（刷盘即销毁），不需要 B+ 树那种持久化优化；跳表的简单性红利最大。
  • 行业背书：LevelDB/RocksDB 用跳表，社区资料多，面试认知成本最低。

选 SkipList 的代价 Cons

  • 最坏复杂度：概率平衡，理论上最坏 O(n)。实践中 kMaxLevel=32 + 随机源质量好时几乎不可能。
  • 缓存局部性差：节点 forward 是分散指针，相比 B+ 树的大节点 cache miss 多。MemTable 体量小时不显著，大时影响读 p99。
  • 内存碎片：每个 SkipNode 独立 new，分配器压力大；RocksDB 用 arena 一次性分配大块 + offset 索引解决。
  • 并发读仍需锁：本实现用 std::shared_mutex，写多时读会被阻塞；RocksDB 用更细粒度的原子读实现 lock-free read。
  • 不持久化：跳表只在内存，崩了靠 WAL 重建；不像 B+ 树本身就在盘上。
为什么不选 B+ 树做 MemTable？ B+ 树的优势是「持久化 + 缓存友好 + 范围扫描」，但这些优势在 MemTable 场景用不上： MemTable 是短命的（刷盘就销毁）、体量小（4MB）、不需要在磁盘上。B+ 树的分裂合并复杂度反而拖累。 真正用 B+ 树的地方是 SSTable 的块内索引——那是磁盘上的，需要缓存友好。
优化路径 · 让跳表更猛 (1) Arena 分配：用一块大内存 + offset，避免每节点 new，缓存局部性 +30%。
(2) 无锁读 + 单写者：forward 用 atomic，读不加锁，写串行化（RocksDB InlineSkipList）。
(3) prefix bloom + hash index：对带前缀的 key 加一层哈希索引，跳过部分跳表查找。
(4) Pin 边界 key：flush 时记录 [min, max]，外部用 key 范围直接跳过整个 MemTable。

3. WAL · Group Commit 的取舍

WAL 每条写入都 fsync 太慢（HDD ≈ 1ms / NVMe ≈ 50μs），完全不 fsync 又不安全。 Group Commit 是「折中点」：kMaxGroupSize=32 或 500μs 超时，leader 一次性 fsync 整组。

Group Commit 的好处 Pros

  • 摊销 fsync：32 条写入共享一次 fsync，单条 WAL 成本下降 32 倍。
  • 吞吐与延迟的平衡：500μs 超时保证单条延迟上限；32 条批量保证吞吐。
  • 无锁唤醒：leader 写完后 group_cv_.notify_all()，follower 一次性唤醒。
  • 崩溃语义清晰：整组原子，要么全可见要么全不可见。

Group Commit 的代价 Cons

  • 单 leader 瓶颈：同一时刻只有一个 leader 在 fsync，高并发下队列积压。
  • 延迟抖动：低并发时单条要等 500μs 超时才提交，p99 偶尔抖。
  • 恢复语义粗：无法区分组内单条，只能整组保留或丢弃。
  • fsync 仍是 syscall：没有绕开系统调用开销。
WAL 的进一步优化方向 (1) Parallel Group Commit：多个 leader 并发 fsync 不同 WAL 文件，类似 MySQL binlog group commit。
(2) Sync WAL bypass：非关键写入（如 cache 预热）用 WriteOptions::disable_wal=true，跳过 WAL。
(3) Direct I/O + 用户态 AIO：绕过 page cache，用 io_uring 批量提交，延迟与吞吐可观测。
(4) Segmented WAL：按 key 分片到多个 WAL，并行 fsync，提高并发上限。
(5) Zero-copy + mmap：WAL 文件 mmap 到内存，写入即落盘（仍需 fsync 元数据）。

4. SSTable · 磁盘布局的取舍

SSTable 选「data block + index block + footer」三段式，块默认 4KB，footer 48 字节固定。这是个工程上反复打磨的结构。

三段式布局的好处 Pros

  • 随机读不读全文件：footer 拿 index_offset → 跳到 index block → 二分定位 data block → 只读那块。
  • 块级压缩：每个 block 独立 Snappy，读时只解压目标块，内存友好。
  • BloomFilter 前置：读 key 前先问布隆，99% 不存在的查询不读 data block。
  • footer 固定大小：48 字节固定，seek(-48) 即可定位，无需扫描。
  • magic 校验：打开即校验，半成品文件秒级识别并丢弃。
  • 版本兼容：format_version 字段区分新旧 block 头，可平滑升级。

三段式布局的代价 Cons

  • 读放大：一次 Get 最多读 N 层 SSTable，每层 BloomFilter + index + data 三次 IO。
  • 空间放大：多版本 + tombstone 占空间，需 Compaction 清理。
  • 写放大：Compaction 反复重写有效数据。
  • block_size 调参难：4KB 适合 HDD，NVMe 上更优可能是 8-16KB。
  • index block 单点：整个 SSTable 只有一个 index，并发读都加载它，cache 压力大。
SSTable 的优化路径 (1) Two-level index：index block 自身也分块，搞二级索引，大文件友好。
(2) Partitioned Index/Filters：RocksDB 把 index 与 bloom 分片到 data block 旁边，按需加载，节省内存。
(3) Prefix Bloom：对前缀查询加二级布隆，scan 优化。
(4) Data block hash index：块内再加 hash 索引，二分变 O(1)。
(5) ZSTD 压缩：比 Snappy 压缩率高 2-3x，CPU 代价略高。
(6) Hash-based SSTable（Cuckoo）：对点查极端优化场景，用 cuckoo hash 替换排序结构。

5. Compaction · 合并策略的取舍

MiniKV 当前用 Leveled Compaction（L0 文件数触发，合并到下层）。 这是 RocksDB 默认策略的简化版，对比 Tiered / FIFO / Hybrid 另有取舍。

策略写放大读放大空间放大适用场景
Leveled（本实现） 高（每层反复重写） 低（每层最多一个文件） 低（最新版本） 读多写少
Tiered 低（每层一次合并） 高（每层多文件） 高（多版本并存） 写多读少
FIFO 最低 中 高 时序数据 / TTL
Hybrid（RocksDB Universal） 中中中 通用，调参难

当前 Leveled 的好处 Pros

  • 读放大可控：每层至多一个有序文件，查询最多 N 次 IO。
  • 空间放大低：同层无重复 key，旧版本及时清理。
  • 实现直观：mergeLevelFiles 一遍 sort + 重建，逻辑清晰。
  • 语义干净：tombstone 在合并到最后一层时安全清除。

当前 Leveled 的代价 Cons

  • 写放大严重：同一 key 可能被合并 10x+ 次，SSD 寿命杀手。
  • L0 是瓶颈：L0 文件间范围重叠，查询要遍历所有 L0。
  • Compaction 风暴：大合并时 IO 打满，影响在线请求延迟。
  • 单线程合并：本实现未做多线程并行 merge，大合并慢。
  • 触发条件简单：只看 L0 文件数，没考虑 level 总大小。
Compaction 的优化路径 (1) Subcompaction：把一个合并任务按 key range 切片到多线程，RocksDB 默认开启。
(2) Rate Limiter：限制 Compaction IO 带宽（rate_bytes_per_sec），避免打满在线请求。
(3) Tiered-then-Leveled：低层 Tiered（写优化）+ 高层 Leveled（读优化），两全。
(4) L0 → L1 Ingest：L0 文件本就有序，可直接 ingest 到 L1 当作首个文件，避免重复合并。
(5) Lazy Compaction：只在读放大超阈值时合并，避免无谓 IO。
(6) Snapshot-aware：跳过被旧 snapshot 引用的 key，避免 GC 卡住。

6. BloomFilter · 双哈希与误判率

BloomFilter 用 murmurHash2(key, 0xbc9f1d34) + murmurHash2(key, 0x9e3779b9) 双哈希， pos = (h1 + i*h2) % bits，默认误判率 1%。

双哈希布隆的好处 Pros

  • memory 单次：只用一次 murmurHash2 计算，不是 num_hashes 次独立哈希。
  • 空间高效：1% 误判率下 bits_per_key ≈ 9.6 bit，10 万 key 仅 120KB。
  • 常量小：num_hashes = bits * ln(2) ≈ 7 次，CPU 友好。
  • 负结果可信：返回「不存在」一定不存在，挡掉 99% 的无效读。
  • 持久化友好：一次写入 + 一次加载，无需重建。

双哈希布隆的代价 Cons

  • 假阳性：1% 概率说「可能存在」但实际不在，仍要读盘。
  • 不能删除：位图不能 reset，tombstone 后 key 仍占位。无法支持删除场景。
  • 哈希相关性：双哈希是 h1 + i*h2 的 Kirsch-Mitzenmacher 方案，理论上次优但实践中够用。
  • 对短 key 不友好：哈希分布依赖 key 长度，短 key 误判率升。
  • 不可合并：多个 SSTable 的 bloom 不能合并，每文件一个。
BloomFilter 的优化方向 (1) Counting Bloom：用计数位代替 bit，支持删除，但内存 4x。
(2) Ribbon Filter / XOR Filter：更省空间（10-30%），支持删除，构造慢但查询快。
(3) SuRF / Trie filter：支持前缀查询的过滤器，范围扫描友好。
(4) Pin hot bloom in memory：热 SSTable 的 bloom 常驻内存，冷文件按需加载。
(5) Per-key prefix bloom：对前缀查询加二级 bloom，scan 优化。

7. BlockCache · LRU 的取舍

BlockCache 用 utils/lru_cache.h，hash map + 双向链表，(path, offset) → Block*。 Compaction 删文件时 invalidatePath 清理对应条目。

LRU + hash 的好处 Pros

  • O(1) 命中 / 淘汰：hash 查找 + 链表头尾操作。
  • 实现简单：~100 行模板代码，无外部依赖。
  • 命中率稳定：对最近访问友好，重复读场景效果显著。
  • 失效精确：Compaction 删文件时按 path 精确清理，不留脏数据。

LRU + hash 的代价 Cons

  • scan 灾难：一次范围扫描可冲掉大半缓存，污染严重。
  • 无优先级：meta block 与 data block 同等地位，热点索引可能被冷数据挤掉。
  • 锁粒度粗：本实现单一互斥锁，高并发读缓存时仍竞争。
  • 无分片：单一大 hash，热点 key 命中率分散差。
  • 不抗负载：突增流量下命中率骤降。
BlockCache 的优化路径 (1) LRU + LFU 混合（W-TinyLFU）：Caffeine 算法，scan 抗污染 + 热点保留。
(2) 分片 ShardedCache：按 key hash 分 N 片，降低锁竞争。
(3) 优先级缓存：index/filter block 与 data block 分池，meta 池小而精。
(4) mmap 直读：对只读 SSTable 直接 mmap，绕过 BlockCache，OS page cache 即缓存。
(5) 压缩块缓存 + 解压块缓存分离：RocksDB 的 block_cache + compressed_block_cache 双池。
(6) 异步预读：扫描场景下 prefetch 下一个 block。

8. MVCC · InternalKey trailer 的取舍

MiniKV 用 user_key(变长) + 8 字节 trailer 的 InternalKey，trailer 把 seq 与 type 打包： packed = (seq << kTypeBits) | type。排序规则：user_key 升序 → 相同 user_key 时 seq 降序。

trailer 方案的好处 Pros

  • 多版本共存：同一 user_key 的多个版本天然有序排在一起，新版本在前。
  • 无需独立索引：seq 直接编码进 key，跳表/SSTable 不需要额外结构。
  • Snapshots 免费：读时给定 seq 即可过滤，seq > reader_seq 的版本跳过。
  • tombstone 也是版本：删除即写入 type=kDeletion，统一处理。
  • 比较函数简单：memcmp 字节序即可，InternalKeyCompare 几行搞定。

trailer 方案的代价 Cons

  • 空间放大：每个版本 8 字节 trailer，多版本场景浪费。
  • GC 延迟：旧版本只在 Compaction 时清理，长 snapshot 会拖累 GC。
  • seq 是引擎级：不是真正的 snapshot isolation，跨事务隔离要靠上层。
  • seq 溢出风险：seq 通常是 56 bit，理论上有溢出问题（实践中几乎不会）。
MVCC 的优化方向 (1) Snapshots 表：维护活跃 snapshot 列表，Compaction 时跳过被引用的旧版本。
(2) Transactional seq：引入 per-transaction seq，支持真正的事务隔离。
(3) seq 压缩：对旧版本批量清理，避免单条清理开销。
(4) Hybrid Logical Clock：用 HLC 替换纯 seq，支持分布式时钟。

9. 整体取舍 · LSM-Tree vs B+ Tree vs Redis

最后把引擎作为一个整体，与 B+ 树（InnoDB）、Redis（dict + RDB+AOF）做横向对比：

维度MiniKV (LSM-Tree)InnoDB (B+ Tree)Redis (dict + AOF)
写性能 顺序写 + 内存追加，10万+/s 原地更新 + fsync，5千/s 内存操作，10万+/s
读性能 多层合并，单次 1-3ms 3-4 层 B+，0.1-1ms 纯内存，<0.1ms
写放大 10-30x 1-2x 1x（AOF）
读放大 N 层 + BloomFilter 固定 3-4 层 1 次 hash
空间放大 中（多版本 + tombstone） 低（原地更新） 低（无多版本）
崩溃恢复 WAL 回放，简单 WAL + redo + undo RDB + AOF replay
数据规模 TB-PB TB-PB GB（内存受限）
范围扫描 有序迭代器 叶子链表 不支持
并发模型 MemTable 锁 + SSTable 无锁读 页锁 + MVCC 单线程 + IO 多线程
典型场景 LSM 日志 / KV / 时序 OLTP / 关系表 缓存 / 会话
整体结论 · 为什么 MiniKV 选 LSM-Tree 目标场景是 结构化 KV 存储 + 写多读少 + 大数据量 + 简单崩溃恢复，这与 LSM-Tree 的优势完全契合：
  • 写优化：追加写内存 + WAL，不触盘不就地更新。
  • 恢复简单：WAL 幂等回放，无需 undo log。
  • 范围扫描：层级有序迭代器天然支持。
  • 实现可控：~3000 行 C++ 实现完整引擎，是面试项目最佳复杂度。
代价是写放大与读放大，通过 BloomFilter / BlockCache / Compaction 优化 + 后续可扩展性（Subcompaction / W-TinyLFU / Ribbon filter）逐步收敛。

10. 设计原则总结

原则 1只追加 · 不可变

WAL / SSTable / Manifest 全部 append-only，崩溃点收敛到「正在写的那个文件」。

原则 2单一真相源

WAL 是写入的真相源，Version 是 SSTable 的真相源，恢复逻辑无歧义。

原则 3幂等恢复

WAL 回放、Manifest 重放都是幂等的，中断恢复可多次重试。

原则 4分层职责

MemTable 写优化，SSTable 读优化，Compaction 收敛放大，每层职责单一。

原则 5概率平衡 > 强制平衡

跳表用概率平衡换取实现简单与并发友好，接受理论最坏换取工程可控。

原则 6摊销 > 单次最优

Group Commit 摊销 fsync，Compaction 摊销合并，用单次延迟换整体吞吐。

原则 7读路径前置过滤

BloomFilter → index → block 三级过滤，把磁盘 IO 降到最低。

原则 8接受放大换简单

写放大 10-30x 是 LSM 的硬代价，换取崩溃恢复简单 + 实现量小。

MiniKV 实现边界（如实告知） 本实现是教学级 LSM-Tree，相比 RocksDB / LevelDB 仍有差距：
(1) 无 Snapshot 列表管理，长事务会拖累 Compaction；
(2) 无 Subcompaction，大合并单线程；
(3) 无 Rate Limiter，Compaction 会抢占在线 IO；
(4) BlockCache 单 LRU 无分片；
(5) 无 Prefix Bloom / Block-based hash index；
(6) Manifest 无 checkpoint，大库恢复慢。
这些都是工程化量产与教学版的关键差距，也是本页面设计分析的优化方向所在。
