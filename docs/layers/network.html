总览/前置接入 / 网络库

Skynet · C++20 协程网络库

Skynet 是项目对外的 :8080 前置网关，用 C++20 协程重写 muduo / libco 思路： epoll ET + 协程化 IO + HTTP 解析 + 反向代理。它不做 JWT/限流， 只负责在 epoll ET + 协程下读完 HTTP（含半包拼包），再 LB/SSE 透传给后端 Gin。

C++20 coroutine epoll ET Task + promise_type HTTP 状态机 负载均衡 SSE 流式

请求处理竖向流程

Skynet 的核心是「主 Reactor accept → Sub Reactor co_await IO → HTTP 解析 → LB 选上游 → 反代」。 下面的竖向流程把每个阶段的关键动作与崩溃点串联起来，每一步都标注归属模块。

1

Main Reactor · accept net/

主线程 IOContext::poll 阻塞等 listen fd，新连接 accept4 拿到 cfd。

关键：用 SO_REUSEPORT 多进程可同时 accept；本实现单进程多线程 round-robin 派发到 Sub。

2

派发到 Sub Reactor net/

cfd 按 round-robin 分给某个 Sub 的 IOContext，EPOLLIN | EPOLLET | EPOLLRDHUP 注册。

崩溃点 A：派发前进程崩 → 连接丢失，客户端 ETIMEDOUT 重连；服务端无状态可恢复。

3

co_await readExact / readUntil net/socket.h

Sub 协程在 asyncRead 上挂起，watchOnce 注册一次性监听；ET 模式必须一次读完到 EAGAIN。

为什么 ET：避免每次事件都触发，减少 syscall；代价是要循环读 EAGAIN 才能停。

4

HTTP 增量解析 http/parser.h

每段数据喂给状态机 METHOD→PATH→VERSION→HEADER→BODY→DONE，半包先缓存，下次拼接再喂。

崩溃点 B：解析一半进程崩 → 客户端连接断开；服务端无任何持久化负担。

5

Router 路由匹配 http/router.h

路径参数提取（/api/:svc/:act），决定后续 handler。

6

LoadBalancer.select() proxy/load_balancer.h

读完 HTTP 后才选上游（不是 accept 时选），用 WRR/LeastConn/ConsistentHash 取 Upstream。

关键：延迟到完整请求后选上游，可基于 X-Hash-Key 头做一致性哈希。

7

ConnectionPool::get proxy/connection_pool.h

复用到后端的 TCP 连接，避免每次握手；连接耗尽则新建（受池上限约束）。

HealthCheck：后台线程周期探活，失败 Upstream 标降级不参与 LB。

8

co_await 转发请求 + SSE 流式回包 proxy/middleware.h

把 HTTP 透传到后端 Gin，Transfer-Encoding: chunked 或 SSE text/event-stream 边收边吐。

崩溃点 C：上游已收部分响应后崩 → 客户端看到截断响应；本实现无重试 chunked，仅对幂等 GET 自动重试。

9

release 连接 + feedback LB proxy/

成功/失败上报给 LB，用于熔断与降级决策；连接还池（若 keep-alive）或关闭。

为什么 skynet 不做 JWT / 限流？ 职责分离：skynet 是「接入层 + 转发层」，只关心 IO；JWT 验签、限流、RBAC 都在 Gin 网关做。 好处：skynet C++ 协程不背业务负担，性能上限只受 IO 限制；Gin 用 Go 写业务易迭代。 缺点：两跳网络，多一次 RTT；可通过同机部署 skynet ↔ Gin 用 UDS 减少 RTT。

核心组件知识点

Task · C++20 协程基础

skynet/include/skynet/core/task.h

Task<T> 是协程的返回值类型，promise_type 管理协程的生命周期与挂起/恢复。

  • promise_type：实现 initial_suspend / final_suspend / return_value / unhandled_exception，桥接 co_await 链式调用。
  • 对称转移：协程挂起时把控制权交还 Executor，恢复时由就绪队列驱动。
  • 资源管理：Task 析构即协程帧释放，避免悬挂引用。

IOContext · epoll ET 事件循环

net/io_context.h · io_context.cpp

IOContext 是 Skynet 的核心事件循环，封装 epoll，支持与协程无缝集成。

  • ET 模式：使用 EPOLLET，事件就绪只通知一次，需一次性读完。
  • watchOnce：一次性监听，触发后立即从 epoll 移除 fd——这是 ET 模式下安全的 re-arm 方式（避免竞态）。
  • add / modify / remove：常规注册 / 改事件 / 注销。
  • poll(timeout_ms)：阻塞等待 kMaxEvents = 1024 个事件，回调驱动协程恢复。
  • 回调表：std::unordered_map<int, Callback>，fd → 回调。

Executor · 协程调度器

core/executor.h · executor.cpp

Executor 是「三路复用」调度：epoll 事件 + 就绪协程队列 + 时间轮定时器，单线程驱动整个事件循环。

  • epoll：IO 就绪 → 恢复等待的协程。
  • 就绪队列：被唤醒的协程先入队，下一轮顺序执行。
  • TimerWheel：时间轮定时器，co_await timeout 在此到期。

TimerWheel · 时间轮定时器

core/timer_wheel.h

用时间轮实现 O(1) 添加 / O(1) 摘除的高效定时器，供协程 co_await sleep 与连接超时使用。

Acceptor / TcpStream / Socket

net/acceptor.h · tcp_stream.h · socket.h

把同步 socket 操作封装成可 co_await 的 Awaitable。

  • Acceptor：协程化 accept，每次新连接返回一个 TcpStream。
  • TcpStream：readExact / readUntil，对 HTTP 半包友好（按分隔符/定长读）。
  • Socket：asyncRead / asyncWrite 返回 Awaitable，内部注册到 IOContext 的 watchOnce。
  • Resolver：协程化 DNS 解析，避免阻塞事件循环。

HTTP 解析 · 增量状态机

http/parser.h · parser.cpp · router.h

HTTP 解析器是增量状态机，适合协程边读边解析的流式场景。

METHOD → PATH → VERSION → HEADER → BODY → DONE
  • 增量解析：每收到一段数据喂给状态机，可中断继续。
  • chunked + pipelining：支持 Transfer-Encoding: chunked 与 HTTP 管道化。
  • Router：路由匹配 + 参数提取。
  • Headers / Response：头部规范化与响应构建。

LoadBalancer · 四种负载策略

proxy/load_balancer.h · load_balancer.cpp

负载均衡器是抽象基类，select() 返回 Upstream；feedback() 反馈成功/失败用于熔断。

  • RoundRobinLB：纯轮询，idx_ 递增取模。
  • WeightedRoundRobinLB：带权轮询，维护 current_weights_（平滑 WRR 算法）。
  • LeastConnLB：最少连接数优先。
  • ConsistentHashLB：一致性哈希，vnodes = 160 个虚拟节点构建 hash ring，buildRing() 初始化。

ConnectionPool + HealthCheck + Upstream

connection_pool.h · health_check.h · upstream.h · middleware.h
  • ConnectionPool：复用到后端的 TCP 连接，避免每次握手；get / release。
  • HealthCheck：后台线程周期探测 Upstream，失败标记降级。
  • Upstream / UpstreamManager：后端实例抽象，被 LB 与池共享。
  • Middleware：代理链中间件钩子。

skynet_gateway · 对外 :8080 前置

skynet/gateway/main.cpp · gateway.yaml

Skynet 的网关示例，读 gateway.yaml 配置后启动协程 accept 循环，把外部请求反向代理到后端 Gin。

  • 职责边界：skynet 不做 JWT、不做限流——这些在 Gin 层；skynet 只做接入与转发。
  • SSE 流式：支持 Server-Sent Events，RAG chat 等流式响应穿透。
  • 主从 Reactor + 协程：Main 只 accept；Sub 上 co_await IO（非阻塞业务线程池模型）。

设计深度分析

下面把 Skynet 的设计决策拆成四类：崩溃恢复（接入层崩溃 vs 上游崩溃 vs 协程崩溃）、 核心技术选型（epoll ET vs LT、协程 vs 回调、watchOnce 一次性监听）、 负载均衡策略对比（RR/WRR/LeastConn/ConsistentHash）、整体取舍与优化方向。

1. 崩溃恢复 · 六种场景

接入层的本质是「无状态转发层」：所有持久化在 Gin 后端，skynet 不持有任何业务状态（除了连接池与 LB 表）。 这决定了 skynet 的崩溃恢复语义与存储引擎完全不同：丢失当前连接是可接受的，重复 / 半截响应是不可接受的。

CASE 1崩溃点 A · accept 后未派发

Main Reactor 已 accept4 拿到 cfd，但还没派发到 Sub 就崩。客户端 SYN/ACK 已完成，会一直等数据 → ETIMEDOUT。

为什么这么设计：接入层无 ack 队列，accept 到派发是原子的两步；中间崩溃必然丢失。 恢复：客户端重连，supervisor 重启 skynet。

恢复语义：连接丢失 · 客户端需重连
CASE 2崩溃点 B · HTTP 解析一半

Sub 已读到部分 HTTP 头，状态机停在 HEADER 阶段就崩。客户端连接断开；服务端协程帧被 Task 析构清理。

为什么这么设计：解析器是无状态字段（每次新协程新 parser），崩溃后无需恢复内存状态。 好处：无 GC 负担，无 WAL，无回放。

恢复语义：连接断开 · 无残留
CASE 3崩溃点 C · 上游已响应一半

skynet 已经把请求转给 Gin，Gin 返回了 HTTP 头与部分 body，skynet 协程正 co_await 转发时崩。 客户端看到截断响应（可能 200 OK + 半截 body），需要业务层检测 Content-Length 不符。

当前实现：无 chunked 重试，仅对幂等 GET 自动换 Upstream 重试；POST/写操作不重试避免重复写入。 优化方向：对非幂等操作用 idempotency-key 头，让上游去重。

恢复语义：客户端看到截断 · 需重试
CASE 4协程泄漏 · await 永不返回

Sub 协程 co_await asyncRead 永久挂起（上游不发数据也不 close），协程帧泄漏。

为什么这么设计：Executor 有 TimerWheel + co_await timeout，配合 shutdown_write_timeout 强制关连接；不依赖业务协程主动检测。

恢复语义：超时强杀 · 协程帧释放
CASE 5连接池中的连接断开

复用的 TCP 连接已 FIN（上游重启或 RST），但 skynet 池里还留着这个 entry。下次 get() 拿到死连接 → 写失败。

当前实现：连接池每次 get 检查 recv(MSG_PEEK) 是否读到 EOF/RST，死连接直接丢弃重建。 缺点：每次 get 多一次 syscall；优化：RST 探测改为基于 epoll 事件的「写失败即丢弃」。

恢复语义：自动重建 · 业务无感
CASE 6skynet 重启 · 滚动升级

supervisor 重启 skynet 进程，listen fd 重新创建，老连接全部断开。客户端按 ETIMEDOUT 重连。

好处：无状态重启快（毫秒级），不像存储引擎要恢复 MemTable；缺点：有损——长连接被中断。 优化方向：用 SO_REUSEPORT + 多进程，逐进程重启实现 zero-downtime；或用 fd passing 把 listen fd 传给新进程。

恢复语义：快速但中断长连接
接入层崩溃恢复的统一原则 状态都在上游 → skynet 崩溃只要快速重启即可，不需要 WAL、不需要快照、不需要 sync。 代价是当前活跃连接全部丢失，但客户端重试成本低（毫秒级）。这是「无状态层换简单恢复」的典型设计。

2. epoll ET vs LT · 为什么选 ET

Skynet 用 EPOLLET（边缘触发），与 muduo（LT）/ libco（LT+hook）形成对比。

维度ET（边缘触发）LT（水平触发）
触发语义 状态变化才通知（fd 从无数据→有数据） 只要 fd 有数据就一直通知
Syscall 次数 每事件一次 epoll_wait + 一次循环读 多次 epoll_wait 持续通知
读循环要求 必须读到 EAGAIN，否则数据滞留 读多少都行，下次还会通知
编程心智 高 · 容易写错 低 · 自然
与协程契合度 高 · 协程 await EAGAIN 切回 Executor 中 · 回调式才方便
thundering herd 多线程 accept 不惊群（仅通知一次） 多线程 accept 惊群
行业先例 nginx / brpc / skynet muduo / libco / golang netpoll（其实是 ET）

选 ET 的好处 Pros

  • 减少 syscall：每次事件触发后必须循环读到 EAGAIN，避免 LT 下重复 epoll_wait。
  • 无惊群：多线程同时 accept 同一 listen fd，ET 只通知一次，避免惊群。
  • 与协程天然契合：协程 await 读 → EAGAIN → 切回 Executor → 等下次事件，逻辑线性。
  • 对延迟敏感场景友好：事件触发立即处理，无 LT 的「重复触发 → 浪费 CPU」。
  • nginx/brpc 行业验证：大规模生产实践稳定。

选 ET 的代价 Cons

  • 必须读完到 EAGAIN：否则下次数据来了也不通知，连接「假死」。
  • 容易写错：漏写 read loop 或误 break 导致数据滞留，bug 极难调试。
  • 边界处理复杂：写缓冲区满时 EPOLLOUT 要切到「写监听」模式。
  • 对短连接不友好：频繁增删 fd，回调表查找开销大。
  • 调试工具少：strace / lsof 看不出 ET 与 LT 区别，要靠源码审查。
为什么 muduo 用 LT？ muduo 作者陈硕在《Linux 多线程服务端编程》中明确说 LT 更不易出错。这是工程优先的选择。 但 skynet 选 ET 的原因：(1) 与 C++20 协程结合更好（await EAGAIN → 切走）；(2) 学习项目追求性能上限； (3) watchOnce 用「一次性监听」绕开 ET 的复杂性——读完立即从 epoll 移除，下次需要再 re-arm，避免竞态。
watchOnce · skynet 的关键工程巧思 ET 模式最大的坑是「读到一半 fd 还有数据没读完，但已经触发过事件了」。 skynet 用 watchOnce 把每次 read 都变成一次性监听：触发即从 epoll 移除 fd → 协程 read 循环 → 不够再 re-arm。 好处：无竞态（不会因为 re-arm 时机错过事件）；缺点：每次 re-arm 多一次 epoll_ctl syscall。 优化方向：对长连接批量预读 + 缓冲区，减少 re-arm 次数。

3. C++20 协程 vs 回调 vs 线程

skynet 用 C++20 协程（Task<T> + promise_type + co_await），对比 muduo 回调与 minikv_server 的线程池。

维度C++20 协程（skynet）回调（muduo）线程池（minikv_server）
并发单位 协程帧（~200B） 闭包（堆分配） 线程栈（默认 8MB）
切换成本 ~10ns（无内核态） 0（直接调用） ~1μs（内核态）
代码可读性 高 · 顺序写 低 · callback hell 高 · 顺序写
栈大小 动态，按需扩 无栈 固定 8MB
编译器支持 需 C++20 + 较新 gcc C++11 即可 C++98 即可
调试 协程帧符号链不直观 栈正常 栈正常
百万连接 可以（每协程 ~200B → 200MB） 可以（无栈） 不行（8MB × 100万 = 8TB）

选 C++20 协程的好处 Pros

  • 代码顺序写：co_await 读 → 解析 → 转发，逻辑像同步代码，可读性高。
  • 无栈开销小：每个协程帧 ~200B，可轻松百万并发。
  • 切换无内核态：promise_type 对称转移，~10ns。
  • 与 ET epoll 契合：await EAGAIN 自动让出，无需手动 yield。
  • 异常传播正常：try-catch 跨 await 点正常工作，不像回调。
  • 是 C++ 现代化趋势：未来更多框架会迁移到协程。

选 C++20 协程的代价 Cons

  • 编译器要求高：需 g++-12+，部分老系统不支持。
  • 调试复杂：协程帧在堆上，gdb 栈符号链不直观，需 -fcoroutines + cmake 支持。
  • 悬空引用风险：co_await 期间引用的局部变量已析构，需用 Task<T> 值语义或智能指针。
  • 无成熟生态：不像 boost.asio/folly 那种 battle-tested。
  • ABI 不稳定：不同编译器协程帧布局不同。
  • 实现量略大：promise_type 接口细节多。
协程的优化方向 (1) 对称协程 vs 非对称协程：当前是 stackless 非对称，可考虑 boost.context 的 symmetric 协程，调度更灵活。
(2) 协程池 + 帧复用：预先分配 N 个协程帧池，避免每次 new。
(3) work-stealing 调度：多线程时各线程偷协程，提高负载均衡。
(4) io_uring 替换 epoll：Linux 5.x 内核的 io_uring 单次 syscall 批量提交 IO，吞吐 ×2-3。
(5) 共享栈协程：libco 风格，多个协程共用一个大栈，省内存（但有切栈开销）。

4. 负载均衡 · 四种策略对比

skynet 同时实现四种 LB：RR / WRR / LeastConn / ConsistentHash，每种适用场景不同。

策略实现复杂度状态依赖session 粘性适用场景
RoundRobin ~20 行 无（仅 idx_） 无 同质后端、轮询均衡
WRR（平滑） ~50 行 current_weights_ 无 异质后端（CPU/内存不同）
LeastConn ~30 行 活跃连接计数 无 请求耗时差异大（长连接）
ConsistentHash ~150 行 hash ring + vnodes 有（同 key 同后端） 缓存场景 / KV 分片

四策略并存的好处 Pros

  • 灵活适配：不同 upstream 集群用不同 LB，配置驱动。
  • 面试加分项：能讲清四种策略的差异与权衡。
  • WRR 用平滑算法：避免突刺，分布均匀。
  • ConsistentHash 用 160 虚拟节点：数据分布均匀 + 单节点宕机影响小。
  • feedback 接熔断：失败累计超阈值自动剔除上游。

四策略并存的代价 Cons

  • 维护成本：4 套实现，bug 容易遗漏。
  • LeastConn 状态难精确：跨线程共享活跃连接计数有锁竞争。
  • ConsistentHash 不支持动态扩容好：加节点需重建 ring，旧映射全失效。
  • 无加权 LeastConn：异质集群无法用最少连接。
  • 无 P2C（Power of Two Choice）：大规模集群的随机采样策略。
LB 的优化方向 (1) P2C（Power of Two Choice）：随机选两个取活跃数少的，比 LeastConn 全局扫描快。
(2) 加权 LeastConn：LeastConn × WRR，异质集群更优。
(3) 动态权重 EWMA：根据延迟与成功率滚动平均调权，自适应故障。
(4) Maglev 算法：Google 的 lookup-table 一致性哈希，O(1) 查找 + 重建快。
(5) 边界探测 + 主动剔除：基于 feedback 累计失败 + 半开探测，避免误杀。
(6) 热重启保 LB 状态：把 LB 内存序列化，重启后恢复，避免 cold start。

5. 主从 Reactor + 协程 vs 单 Reactor + 线程池

skynet 用 Main Reactor（accept）+ N 个 Sub Reactor（co_await IO），与 minikv_server 的「单 Reactor + 线程池」对比。

主从 Reactor + 协程的好处 Pros

  • 分压：accept 不被 IO 阻塞，新连接接入不抖动。
  • 多核利用：Sub Reactor 各自 epoll，CPU 多核负载均衡。
  • 无锁连接派发：每个 Sub 独占自己 cfd 集，accept → round-robin 派发无锁。
  • 协程让 IO 不阻塞：每个 Sub 单线程 + 协程，IO 阻塞不浪费线程。
  • 对慢连接友好：慢客户端不拖累快客户端。

主从 Reactor + 协程的代价 Cons

  • 派发不均：round-robin 派发可能让某 Sub 过载。
  • 跨 Sub 难迁移：cfd 在某 Sub epoll 中，要迁移需先 remove 再 add，开销大。
  • 协程帧在堆：高并发下堆分配压力大。
  • 无业务线程池解耦：慢业务（如 DB 查询）阻塞协程，必须配合 thread_pool 跑业务。
  • 调试复杂：N 个 Sub 线程，gdb 切换累。
主从 Reactor 的优化方向 (1) work-stealing 派发：各 Sub 队列长度上报，Main 优先派给短队列。
(2) io_uring 多 Sub：每个 Sub 一个 io_uring 实例，syscall 摊销到批量提交。
(3) SO_REUSEPORT 多 Main：多进程同时 accept，scale 到多 CPU。
(4) 动态 Sub 数：按连接数自动扩缩 Sub 线程。
(5) 异步 DNS 缓存：Resolver 协程化 + 进程内 DNS 缓存，避免每次反代都解析。

6. HTTP 解析 · 增量状态机 vs 全量解析

skynet 用「增量状态机」逐段喂给 parser，对比「先收全包再一次性解析」。

增量状态机的好处 Pros

  • 无需缓冲整个请求：边收边解析，header 大可立即路由。
  • 提前拒绝：method/path 一解析完就能拒绝非法请求，不读完 body。
  • 支持 chunked + pipelining：多请求复用连接。
  • 内存友好：小 buffer 即可，避免大请求 OOM。
  • 与协程契合：await read → feed parser → await more。

增量状态机的代价 Cons

  • 状态机实现复杂：边界条件多（header 跨包、CRLF 跨包）。
  • 调试难：需要单元测试覆盖所有跨包场景。
  • 慢攻击难防：慢速发送 header 会一直占用协程，需要 timeout 配合。
  • chunked 边界：Transfer-Encoding: chunked 的边界解析易错。
  • 无压缩支持：HTTP/2 的 HPACK 头压缩不支持。
HTTP 解析的优化方向 (1) simd 解析：picohttpparser 用 SIMD 加速 CRLF 查找，吞吐 ×3。
(2) HTTP/2 支持：HPACK 头压缩 + 多路复用。
(3) 慢速攻击防御：header timeout + max_header_bytes + max_body_bytes。
(4) zero-copy：read 到 ringbuffer，parser 用 offset 而非 copy。
(5) HTTP/3 over QUIC：基于 UDP，无队头阻塞，但需重构 IO 层。

7. 整体取舍 · skynet vs nginx vs envoy

维度skynetnginxenvoy
语言 C++20 协程 C + 回调 C++ + 协程
并发模型 多线程 Reactor + 协程 多进程 + 事件回调 多线程 + 协程
HTTP 解析 自研状态机 SIMD 加速 HTTP/1+2+3
负载均衡 4 种 3 种（RR/IP/Hash） 10+ 种 + xDS
服务发现 无（配置文件） 无 xDS / SDS / EDS
熔断 / 重试 feedback + GET 重试 upstream_check 完整熔断器 + 重试预算
observability 无内置 access_log 全链路 tracing + metrics
定位 教学项目 Web 服务器 / 反代 Service Mesh Proxy
整体结论 · 为什么 skynet 选 C++20 协程 + ET + 多 Reactor 目标场景是「面试项目 + 高并发接入层 + 易读代码」：
  • C++20 协程：代码可读性接近同步，是 C++ 现代化趋势，面试加分。
  • ET epoll：性能上限更高，与协程契合，行业先例多。
  • 多 Reactor：分压 + 多核利用，是接入层标配。
  • 四策略 LB：覆盖主流场景，配置驱动易扩展。
代价是生态未成熟、调试复杂、无 envoy 那种 service mesh 能力——这些是用「教学项目 + 简单」换来的取舍。

8. 设计原则总结

原则 1无状态

接入层不持有业务状态，崩溃后立即重启可恢复，恢复简单。

原则 2ET + 协程

ET 减少 syscall，协程让代码线性可读，await EAGAIN 自动让出。

原则 3watchOnce 避竞态

一次性监听 + re-arm 绕开 ET 的复杂边界，简化心智。

原则 4职责分离

skynet 只做 IO，JWT/限流/RBAC 都在后端 Gin，C++ 不背业务负担。

原则 5读完再选上游

LB 在完整 HTTP 后选上游，支持基于 header 的一致性哈希。

原则 6超时驱动一切

TimerWheel 让协程不会永久挂起，避免协程泄漏。

原则 7幂等才重试

GET 自动重试，POST/写操作不重试，避免重复写入。

原则 8接受丢连接换简单

无状态重启有损，但成本低（ms 级）；不需要 WAL/snapshot/恢复。

skynet 实现边界（如实告知） 本实现是教学级接入层，相比 nginx / envoy 仍有差距：
(1) 无 HTTP/2 / HTTP/3 支持；
(2) 无 service discovery（只能读 yaml 配置）；
(3) 无完整熔断器（只有 feedback + HealthCheck，无半开探测）；
(4) 无 observability（access_log / metrics / tracing 都需另加）；
(5) 无 SIMD 加速的 HTTP 解析；
(6) 无 io_uring 优化（仍是 epoll）。
这些都是教学版与生产版的差距，也是本页面设计分析的优化方向所在。
