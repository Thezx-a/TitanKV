Auth 服务知识点

JWTManager · Access + Refresh 双 Token

services/auth/jwt.go
  • Access Token：短期 30min，携带 user_id / role / jti。
  • Refresh Token：长期 7d，不带 role——刷新时重新查角色，避免角色变更后 Refresh 仍带旧角色。
  • jti：uuid.NewString()，唯一 ID 用于吊销。
  • 签名：HS256，Parse 强制 SigningMethodHMAC，拒绝 alg:none。
  • TTL 暴露：AccessTTL() / RefreshTTL() 给 Redis 设过期时使用。

password · bcrypt 密码哈希

services/auth/password.go

用 bcrypt 做密码哈希，自带盐与可调成本因子，抗暴力破解与彩虹表。

apikey · 服务端只存 SHA256

services/auth/apikey.go

APIKey 签发后只在 DB 存 SHA256(key)；校验时对入参做 SHA256 比对，DB 泄露也无法还原原 Key。

rbac.go · 角色权限定义

services/auth/rbac.go

权限命名 resource:action（kv:get / kv:put / rag:ingest），与网关 middleware/rbac.go 对齐。

store.go · 用户持久化

services/auth/store.go · client.go · handler.go

用户表存储 + Gateway 调用 Auth 的 HTTP client（注册/登录/刷新/登出/apikey Handler）。

RAG 服务 · 检索增强生成全链路

RAG 是本层最复杂的服务，从文档入库到流式问答一条龙。下面把入库与查询两条路径竖向展开。

入库 · ingest (rag:ingest)

1

Document 接入 ingest.go

接收上传文档（文本 / markdown / pdf），写入临时缓冲。

崩溃点 A：接入后未分块就崩 → 客户端重试；服务端无残留。

2

chunker · 文档分块 chunker.go

按字符 / 段落滑窗切分，chunk_size=512, overlap=64。

3

embedding · 向量化 embedding.go

每块调 embedding 模型 API，得到 dim=768 的向量。

崩溃点 B：部分块 embed 完后崩 → 已 embed 的入索引，未 embed 的需客户端重试；本实现无事务回滚。

4

hnsw_index.Add() hnsw_index.go

从顶层 greedyClosest 下降 → 目标层 searchLayer 选邻居 → 双向连边。

关键：m=16, ml=1/log(16)，概率分层，无锁插入需 sync.RWMutex。

5

WriteBatch · 写 MiniKV store.go

向量 + chunk 文本分别以 vec:<id> / chunk:<id> key 写入 MiniKV。

崩溃点 C：MiniKV 写一半崩 → WAL 恢复幂等；但 HNSW 索引内存状态不持久化（重启需 SaveSnapshot 重建）。

查询 · chat (rag:query)

1

Query 接入 chat.go

接收用户问题，可能含多轮对话历史。

2

embedding · 查询向量化 embedding.go

问题用相同 embedding 模型转成向量。

3

hnsw_index.TopK(k) hnsw_index.go

顶层贪心下降 → 底层 searchLayerLocked(ef=k*4) 取候选 → 余弦相似度排序。

崩溃点 D：查询中途崩 → 客户端 SSE 连接断开；服务端协程泄漏由 ctx timeout 兜底。

4

retrieve · 回查 chunk retrieve.go

根据向量 ID 回查 chunk:<id>，拿原文片段。

5

rerank · 重排 rerank.go

对 TopK 候选做二次相关性打分，提升最终精度。

6

llm · prompt 拼装 llm.go

把问题 + rerank 后的 chunk 拼成 prompt，调大模型。

崩溃点 E：LLM API 不可达 → 返回 502；本实现无 fallback 模型。

7

chat · SSE 流式输出 chat.go

把 LLM 输出按 token chunk 流式吐给前端，text/event-stream。

崩溃点 F：客户端断连 → 服务端继续生成（浪费 token）或 ctx cancel 检测断开。

为什么 RAG 用 HNSW 不用暴力搜索？ 暴力搜索 O(N) 对每查询都遍历全部向量，N=100 万时单次 >500ms。HNSW 是工业级 ANN 算法， 理论 O(log N) 实际查询，10 万向量 TopK=10 仅需 ~5ms。 代价是构建慢（O(N log N)）+ 内存大（每向量多个邻居指针）+ 不能精确（recall 95%+）。 详见本页设计分析第 3 节。

HNSWIndex · 分层小世界图

services/rag/hnsw_index.go

近似最近邻搜索（ANN）的工业级算法。本项目实现了一个简化版 HNSW，接口与暴力 SideIndex 兼容，便于在 N 增长时无缝切换。

  • 参数：m = 16（每层最大邻居数）、ml = 1/log(16)（层高分布系数）。
  • 随机层：randomLayer() 以 0.5 概率递增，封顶 8 层。
  • 插入 Add()：从顶层 greedyClosest 下降 → 在目标层 searchLayer(ef=m*2) 选邻居 → 双向连边。
  • 查询 TopK()：顶层贪心下降 → 底层 searchLayerLocked(ef=k*4) 取候选 → 返回 TopK Hit（按余弦相似度排序）。
  • searchLayer：候选集 + 已访问集合，ef 控制精度，超限时按相似度裁剪。
  • 相似度：cosine(query, vec) 余弦相似度。
  • 持久化：SaveSnapshot / SaveSnapshotPrefix / MergeSnapshot，JSON 存向量。
  • 按前缀清空：ClearByPrefix 支持 Collection 级删除。

VectorIndex 抽象 + SideIndex

vector_index.go

VectorIndex 接口抽象了 HNSW 与暴力 SideIndex，NewVectorIndex(dim, "hnsw") 按环境变量 RAG_INDEX_TYPE 选择实现。

chunker / embedding / rerank / llm

chunker.go · embedding.go · rerank.go · llm.go
  • chunker：文档分块（按字符/段落滑窗）。
  • embedding：文本 → 向量，封装 embedding 模型 API。
  • rerank：对 TopK 候选重排，提升相关性。
  • llm：拼装 prompt 调大模型，返回生成文本。

retrieve / ingest / chat / store

retrieve.go · ingest.go · chat.go · store.go · eval.go
  • retrieve：从向量库取相关 chunk。
  • ingest：入库主流程，串起 chunker → embedding → index。
  • chat：多轮对话 + 知识问答，SSE 流式输出。
  • store：文档与向量索引存储层。
  • eval：检索质量评测，eval_test.go。

设计深度分析

下面把微服务层的设计决策拆成四类：崩溃恢复（按服务分别看）、 核心技术选型（HNSW vs 暴力搜索 / bcrypt vs argon2 / 独立进程 vs 单体）、 服务间通信（HTTP vs gRPC vs MQ）、整体取舍与优化方向。

1. 崩溃恢复 · 五种服务场景

微服务层是有状态服务 + 无状态接入的混合：Auth 持 Redis jti，Data 持 MiniKV 连接，RAG 持 HNSW 内存索引。 崩溃语义各不相同。

CASE 1Auth 服务崩溃

Auth 进程崩。Redis jti 黑名单仍在 Redis 中持久化；用户表在 MiniKV 不丢失。 重启后 Auth 进程继续读写 Redis 与 MiniKV。

影响：注册 / 登录 / 刷新 / API Key 签发短暂不可用 → 网关返回 502。 恢复：supervisor 重启，毫秒级恢复。优化：多副本 + K8s liveness probe 自动重启。

恢复语义：状态在 Redis / MiniKV · 快速重启
CASE 2Data 服务崩溃

Data 进程崩，MINIKV_ADDR 连接断开。MiniKV 数据仍在，下次重启 Data 自动重连。

影响：KV 读写不可用 → 网关 502。 恢复：重启重连，毫秒级。优化：多副本 + LB，单副本崩不影响整体。

恢复语义：无状态 · 重连即可
CASE 3RAG 服务崩溃 · HNSW 内存丢失

RAG 进程崩。HNSW 索引在内存中，重启后从 SaveSnapshot 重建，向量原数据在 MiniKV 不丢。

为什么这么设计：HNSW 索引构建慢（O(N log N)），但读快；持久化用 JSON 快照，重启时一次性加载。 代价：大索引重建慢（100 万向量 ~10s）；优化：(1) 周期性自动 snapshot；(2) 用 mmap 持久化，零拷贝加载；(3) 用 FAISS / Milvus 等成熟向量库。

恢复语义：重建索引 · 慢
CASE 4Meta 服务崩溃 · Schema 丢失

Meta 进程崩。Schema 在 MiniKV 不丢；watcher 监听断开，订阅者短暂收不到变更事件。

影响：Schema 查询不可用；watcher 重启后需要 catch-up 重新订阅。 优化：(1) Meta 把变更事件写 MiniKV，watcher 重启时回放；(2) 用 etcd watch 替代自实现 watcher。

恢复语义：Schema 在 KV · watcher 重订阅
CASE 5Observability 服务崩溃

Observability 进程崩。scraper 周期采集中断，Prometheus 抓不到数据；历史指标仍在。

影响：监控短期盲区；Prometheus 抓取失败告警。 恢复：重启 scraper 继续采集；监控是只读，崩了不影响业务。

恢复语义：只读 · 不影响业务
微服务崩溃恢复的统一原则 状态外置 → 服务本身无状态或薄状态：Auth 把 jti 放 Redis，Data 把数据放 MiniKV，Meta 把 Schema 放 MiniKV。 好处：任意服务崩了重启即恢复；代价：RAG 的 HNSW 索引内存态重建慢，需特殊处理。

2. Auth · bcrypt vs argon2 · 密码哈希选型

Auth 用 bcrypt 做密码哈希，对比 argon2 / scrypt / PBKDF2。

维度bcrypt（本实现）argon2scryptPBKDF2
算法 Blowfish 派生 是 PHC winner 内存硬 通用 KDF
抗 GPU/ASIC 中 高（内存硬） 高 低
Go 标准库 golang.org/x/crypto/bcrypt 需引入 argon2 lib 需引入 crypto/pbkdf2
易用性 一行 GenerateFromPassword 需调参 需调参 易用
行业先例 Django / Rails / Spring 新系统首选 Litecoin / Dropbox 老系统

选 bcrypt 的好处 Pros

  • Go 标准库：x/crypto/bcrypt 一行调用，自带盐。
  • 抗彩虹表：自带随机盐，同密码不同哈希。
  • 可调成本：cost=10，硬件升级可调高。
  • 生态成熟：大多数后端框架默认。

选 bcrypt 的代价 Cons

  • 抗 GPU 不如 argon2：不内存硬，GPU 暴力破解友好。
  • 密码长度限制 72 字节：长密码会被截断（需预 SHA256）。
  • 不是 PHC winner：新项目应该选 argon2id。
  • cost 难动态调：已存哈希 cost 固定，升级需重新哈希。
密码哈希的优化方向 (1) 迁移到 argon2id：PHC winner，内存硬，抗 GPU。
(2) 密码预哈希：对 >72 字节密码先 SHA256，避免 bcrypt 截断。
(3) pepper：哈希前加 server-side secret，DB 泄漏 + pepper 未知仍难破。
(4) 慢哈希迁移：登录时若哈希算法过期，重新用新算法哈希后存回，透明迁移。

3. RAG · HNSW vs 暴力搜索 · 向量索引选型

RAG 默认用 HNSW（RAG_INDEX_TYPE=hnsw），可切换 SideIndex（暴力）。

维度HNSW（本实现）暴力 SideIndexIVFFAISS-IVF-PQ
查询复杂度 O(log N) O(N) O(√N) O(log N) 近似
构建复杂度 O(N log N) O(1) O(N) O(N)
内存 大（每节点 m 个邻居指针） 仅向量 中 小（PQ 压缩）
召回率 95%+ 100% 90%+ 85%+
持久化 复杂（图结构） 仅向量 中 中
实现量 ~600 行 ~30 行 ~200 行 用现成库
N=10万查询延迟 ~5ms ~500ms ~20ms ~3ms

选 HNSW 的好处 Pros

  • 查询快：O(log N)，10 万向量 ~5ms，符合在线 RAG 实时性。
  • 召回率高：95%+，足够 RAG 场景（不要求 100% 精确）。
  • 插入实时：Add() 可在线插入，不需重建索引。
  • 参数少：m / ml / ef 三个参数好调。
  • 接口与 SideIndex 兼容：可平滑切换，便于测试对比。
  • 行业主流：faiss-hnsw / Milvus / NMSLIB 都用 HNSW。

选 HNSW 的代价 Cons

  • 内存大：每向量 ~16 个邻居指针，N=100万内存 ~400MB。
  • 构建慢：O(N log N)，10 万向量构建 ~30s。
  • 持久化复杂：图结构 JSON 序列化，文件大；mmap 持久化需重写。
  • 删除难：HNSW 不支持高效删除，需标记墓碑或重建。
  • 并发难：插入需锁，影响查询吞吐。
  • 不能精确：95% 召回，剩余 5% 可能漏关键 chunk。
为什么不直接用 FAISS / Milvus？ FAISS / Milvus 是成熟向量库，性能 / 功能 / 工程化都远超自实现 HNSW。但本实现自写 HNSW：
  • (1) 学习目的：理解 HNSW 算法，面试能讲清细节。
  • (2) 无外部依赖：纯 Go 实现，部署简单。
  • (3) 可定制：嵌入 MiniKV key 空间，与 LSM-Tree 集成。
生产场景应该用 Milvus / Qdrant / Weaviate 等成熟向量库。
HNSW 的优化方向 (1) mmap 持久化：用 mmap 替代 JSON 序列化，零拷贝加载，10x 加速。
(2) 分片索引：按 collection 分索引，避免单索引膨胀。
(3) 墓碑删除：标记删除而非物理删除，定期重建清理墓碑。
(4) PQ 量化压缩：对向量做乘积量化，内存省 8-16x。
(5) 并发优化：分片锁 / 无锁读，提高并发查询吞吐。
(6) GPU 加速：对 GPU 友好的 IVF-PQ 替代，吞吐 ×100。

4. 服务间通信 · HTTP vs gRPC vs MQ

当前所有服务间走 HTTP（Gateway → Auth/Data/Meta/Observ/RAG），对比 gRPC 与 MQ。

维度HTTP / RESTgRPCMQ（Kafka/NATS）
序列化 JSON（文本） Protobuf（二进制） 多种
性能 5-10k QPS 50-100k QPS 异步
流式 SSE（单向） 双向流 天然
调试 curl / 浏览器直连 需 grpcurl 需 MQ 工具
解耦 同步耦合 同步耦合 异步解耦
IDL 无 .proto 文件 schema registry

选 HTTP 的好处 Pros

  • 实现简单：Go net/http + JSON，几行搞定。
  • 调试友好：curl / Postman / 浏览器都行。
  • SSE 流式：chat 用 text/event-stream，浏览器原生支持。
  • 生态成熟：中间件 / 监控 / 文档生成工具链完整。
  • 无 IDL 依赖：不需要 protoc 编译步骤。

选 HTTP 的代价 Cons

  • 序列化慢：JSON 比 protobuf 慢 5-10x，体积大 2-3x。
  • 无 schema：字段拼写错只能运行时发现。
  • 无双向流：chat 只能 SSE 单向，无法双向。
  • 无重试预算：gRPC 自带 deadline propagation。
  • 同步耦合：无 MQ 异步解耦，服务故障传播。
  • 无 backpressure：慢消费者拖累服务端。
服务间通信的优化方向 (1) gRPC + protobuf：对内部服务通信用 gRPC，吞吐 ×5-10。
(2) NATS / Kafka 异步：对 ingest 用 MQ 解耦，文档入库异步处理。
(3) GraphQL BFF：前端聚合用 BFF 一次取多服务数据。
(4) 服务网格 Istio：把熔断 / 重试 / observability 下沉到 sidecar。
(5) 双向流 gRPC：RAG chat 用双向流替代 SSE，体验更好。
(6) schema registry：JSON 也加 schema 验证，避免拼写错。

5. 整体取舍 · 单体 vs 微服务 vs Service Mesh

维度微服务（本实现）单体Service Mesh
开发速度 中 快（无网络） 慢（sidecar 配置）

整体结论 · 为什么选 5 微服务拆分 目标场景是「面试项目 + 演示分层 + 不同技术栈」：
  • 职责单一：Auth 只做鉴权，Data 只做 KV，RAG 只做检索生成，边界清晰。
  • 故障隔离：RAG 重启不拖累 Auth / Data。
  • 独立扩展：RAG 流量大时单独扩 RAG。
  • 覆盖技术栈：覆盖 HTTP / SSE / 原生 TCP / Redis 多种通信模式。
代价是多一次网络 RTT + 5 套监控部署成本——适合演示与面试，不适合生产小团队。

6. 设计原则总结

原则 1状态外置

状态放 Redis / MiniKV，服务本身无状态，崩了重启即恢复。

原则 2职责单一

每服务一个职责，Auth 只鉴权、Data 只 KV、RAG 只检索。

原则 3接口抽象

VectorIndex 抽象 HNSW 与 SideIndex，可平滑切换。

原则 4HTTP + SSE 易调试

服务间通信用 HTTP/SSE，调试友好，符合教学场景。

原则 5环境变量配置

配置走环境变量 + 默认值兜底，无外部配置文件依赖。

原则 6内存回退

无 MiniKV 时 Data 回退内存 store，本地快速跑通。

原则 7HNSW 内存态重建

RAG 索引内存态，重启重建慢；接受换取查询快。

原则 8无事务回滚

ingest 中途失败不回滚，已 embed 的入索引，未 embed 的需重试。

微服务实现边界（如实告知） 本实现是教学级微服务层，相比生产环境仍有差距：
(1) 无 gRPC，全 HTTP 性能受限；
(2) 无服务发现，靠环境变量；
(3) 无服务网格（Istio），熔断 / 重试需自实现；
(4) HNSW 是简化版，无 PQ 量化、无 mmap 持久化；
(5) RAG 无事务回滚，ingest 失败部分入库；
(6) Observability 仅 scrape，无 push gateway。
这些都是教学版与产品级微服务的差距，也是本页面设计分析的优化方向所在。
