总览/网关层

API Gateway · Go + Gin

Gin 网关是请求进入业务域的第一道关卡：用洋葱模型串起 RequestID/Logger/Recover/RateLimit/Auth/RBAC， 再按前缀反向代理到各微服务。它从环境变量读配置，Redis 不可用时降级为无限制。

Go 1.23 Gin 洋葱中间件 JWT + APIKey RBAC Redis 限流 优雅停机

请求处理竖向流程 · 洋葱中间件链

中间件按注册顺序包裹，外层先执行 before、内层先执行 after。顺序很关键：Recover 必须在 Logger 之后（Logger 才能记到 panic），Auth 必须在 RBAC 之前（先识别身份再判权限）。

1

RequestID middleware/request_id.go

生成 uuid，写入 X-Request-ID 头 + c.Set("request_id")，串联后续日志与追踪。

关键：优先读客户端传入的 X-Request-ID（兼容上游追踪），否则新建。

2

Logger middleware/logger.go

结构化记录 method/path/status/latency，附 RequestID；Recover 在其后才能记 panic。

3

Recover middleware/recover.go

defer recover() 捕获 panic，记日志后返回 500，进程不崩。

崩溃点 A：Handler panic 由 Recover 接住 → 500 响应 + 进程存活；否则会挂掉整个 Gin worker。

4

RateLimit middleware/ratelimit.go

Redis Lua 令牌桶 burst=100, sustained=10/s；Redis 不可用时降级放行。

崩溃点 B：Redis 抖动 → 降级无限制；否则会让全部请求被限流。

5

Auth · 你是谁 middleware/auth.go

优先 Bearer JWT（强制 HMAC 拒 alg:none），其次 X-API-Key；jti 黑名单查 Redis。

崩溃点 C：Redis 查 jti 失败 → 放行（不阻断）；否则全量 401。

失败 401：缺 token / 解析失败 / 已吊销。

6

RBAC · 你能干啥 middleware/rbac.go

基于 role 查权限矩阵，required 权限未命中返回 403。

细粒度方法映射：GET=kv:get / POST|PUT=kv:put / DELETE=kv:delete。

失败 403：身份已识别但权限不足。

7

ReverseProxy · 前缀路由 + 身份注入 handler/proxy.go

按 prefix → target 选上游，注入 X-User-ID / X-Role / X-Request-ID。

崩溃点 D：上游服务不可达 → 502 Bad Gateway；客户端收到错误响应。

8

Handler 业务处理 backend services

Data / Meta / Observability / RAG 后端 Gin 处理请求，可能写 MiniKV。

崩溃点 E：业务协程 panic 由 Recover 兜底；MiniKV 写失败由后端事务层兜底。

9

回弹 · 洋葱倒序 after

Handler 返回 → RBAC.after → Auth.after → RateLimit.after → Logger.after → RequestID.after → 响应客户端。

关键：全程同一 goroutine，X-Request-ID 贯穿日志与追踪。

为什么 Recover 必须在 Logger 之后？ Logger 的 c.Next() 调用后等待内层结束；若 Recover 在 Logger 内层，Handler panic 会先被 Recover 接住， 再回弹到 Logger，Logger 才能记到 panic 日志。如果反过来，Recover 在最外层，panic 先被 Recover 接住但 Logger 已退出，记不到。

核心组件知识点

router.go · 路由注册与反向代理映射

gateway/router.go

所有路由与中间件链在此编排，环境变量驱动配置。

  • Config：从环境变量读 GATEWAY_ADDR / JWT_SECRET / REDIS_ADDR / *_SERVICE_URL，getenv() 带默认值兜底。
  • 中间件链：gin.Recovery() + metrics.GinMiddleware + RequestID→Logger→Recover→RateLimit。
  • 无鉴权：GET /ping、GET /healthz、POST /api/auth/{register,login}。
  • 鉴权组：POST /api/auth/{refresh,logout,apikey}，apikey 还需 apikey:issue 权限。
  • 反向代理 map：/api/data → :8081、/api/meta → :8083、/api/observability → :8084、/api/rag → :8085。
  • RBAC 分流：data/meta/observability 按方法映射 KV 权限；rag 区分 retrieve/chat=rag:query 与其他写=rag:ingest。
  • 优雅停机：SIGINT/SIGTERM → srv.Shutdown(5s)。

Auth · JWT + APIKey 双轨

gateway/middleware/auth.go

识别「你是谁」：优先 Bearer JWT，其次 X-API-Key。失败统一 401。

// 优先级
1) Authorization: Bearer <jwt>   → parseJWT → 检查 jti 黑名单
2) X-API-Key: <key>              → 调 Auth 服务 VerifyAPIKey
3) 都没有 → 401 unauthorized
  • alg:none 防御：parseJWT 强制 SigningMethodHMAC，拒绝 alg:none 伪造攻击。
  • jti 黑名单：登出时把 jti 写入 Redis revoked:jti:<id>，TTL = token 剩余有效期。
  • Redis 故障放行：isRevoked 查询失败时返回 false，避免 Redis 抖动阻断全部请求。
  • 上下文注入：c.Set("user_id" / "role" / "auth_method") 给后续中间件。
  • APIKey 哈希：HashAPIKey 服务端只存 SHA256，DB 泄露不暴露原 Key。

  • 扩展：生产可换为基于 etcd 的动态服务发现。

设计深度分析

下面把网关的设计决策拆成四类：崩溃恢复（中间件链 / 上游服务 / Redis 三种场景）、 核心技术选型（JWT + jti 黑名单 vs Session、Redis 令牌桶 vs 滑动窗口、洋葱中间件 vs Filter Chain）、 RBAC 权限模型（基于角色 vs 基于 ACL）、整体取舍与优化方向。

1. 崩溃恢复 · 五种场景

网关是有中间状态但无持久化的层：Redis 是依赖（jti 黑名单 / 限流），但 Redis 不可用要走降级；上游服务会失败，要做熔断与重试。 核心不变量：JWT 自验证 + Redis 可降级 + 上游失败可回滚。

CASE 1崩溃点 A · Handler panic

业务 Handler panic（如 nil 指针、越界访问）。Recover 中间件 defer recover() 接住，记日志返回 500，进程不崩。

为什么这么设计：Go 协程 panic 不接住会拖死整个进程；gin.Recovery() 在最外层接住所有 panic。 好处：进程存活，其他请求不受影响；缺点：状态可能不一致（如已开始写 MiniKV 中途 panic）。

恢复语义：500 响应 · 进程存活
CASE 2崩溃点 B · Redis 限流不可用

Redis 抖动 / 宕机，RateLimit Lua 脚本调用失败。当前实现降级放行，不限流。

为什么这么设计：限流是附加能力不是必需；宁可放过流量也不阻断业务。代价：Redis 抖动期间可能被刷爆。 优化方向：本地 fallback 用 golang.org/x/time/rate token bucket，进程内限流 + Redis 协同限流。

恢复语义：降级放行 · 风险过载
CASE 3崩溃点 C · Redis jti 黑名单查询失败

Redis 暂时不可达，isRevoked(jti) 查询失败。当前实现返回 false，即认为 token 未吊销，放行。

为什么这么设计：避免 Redis 抖动让全部请求被踢 401；代价：登出的 token 在 Redis 故障期间仍可用。 优化方向：本地缓存一份最近吊销的 jti 短期 TTL，配合「Redis 失败 → 用本地缓存兜底」策略。

恢复语义：放行可能已吊销 token · 安全降级
CASE 4崩溃点 D · 上游服务不可达

httputil.ReverseProxy 转发到 Data/Meta/RAG，上游宕机返回 502/连接拒绝。

当前实现：仅返回 502；无重试（避免非幂等操作重复写入）。 优化方向：(1) 上游服务多副本 + LB（skynet 已支持）；(2) 对幂等 GET 自动重试 1-2 次；(3) 熔断器：失败累计超阈值 → 暂停转发 + 周期性半开探测。

恢复语义：502 · 客户端重试
CASE 5优雅停机 · SIGTERM

K8s/Supervisor 发 SIGTERM，srv.Shutdown(5s) 拒新连接，等已有连接处理完。

为什么这么设计：避免请求半截被杀。缺点：5s 不够长连接 keep-alive，可能丢；优化：停机前从 K8s endpoints 摘除 + 等 grace 期结束才真正退出。

恢复语义：无中断退出
为什么网关依赖 Redis 但 Redis 不可用不阻断业务？ 网关的设计哲学是「Redis 是优化项不是关键依赖」：JWT 自验证（HMAC）不需要 Redis； 限流和 jti 黑名单是 Redis 提供，但都设计了降级路径。这避免了「Redis 抖一下全站挂」的连锁故障。 代价是 Redis 故障期间安全降级（放过已吊销 token），需要配合监控告警及时发现。

2. JWT + jti 黑名单 vs Session · 为什么选 JWT

网关用 JWT + Redis jti 黑名单双轨，对比传统 Session。

维度JWT + jti 黑名单Session（Redis 存）
验证方式 本地 HMAC 验签，无网络往返 查 Redis / DB
水平扩展 无状态，任意网关实例都能验 需 sticky session 或共享存储
撤销 需要 jti 黑名单（Redis） 直接删 Session 即可
大小 1-2KB（含 payload） 仅一个 sid cookie
过期 自带 exp，到期自动失效 需服务端定时清理
跨域 Bearer 头，跨域友好 需 cookie + CORS
移动端 / API 天然适合 不适合

JWT + jti 黑名单的好处 Pros

  • 无状态验签：HMAC 本地验，无 Redis 往返，p99 低。
  • 水平扩展友好：多实例网关都能验，不需要共享 Session。
  • 自带过期：exp 字段到期自动失效，无需服务端清理。
  • API Key 互补：对外服务用 API Key，对内用户用 JWT。
  • 跨域友好：Bearer 头，无 cookie + CORS 问题。

JWT + jti 黑名单的代价 Cons

  • 撤销难：JWT 一旦签发无法回收，需 Redis 维护 jti 黑名单。
  • 体积大：含 payload，HTTP 头开销比 Session cookie 大。
  • 密钥泄漏风险：HMAC 密钥泄漏则所有 token 伪造，需轮换机制。
  • alg:none 攻击：必须强制 SigningMethodHMAC，本实现已防。
  • 无法中途改权限：role 在 payload 中签发后不可改，需配合短期 token + refresh。
  • 黑名单查询每次 Redis：性能依赖 Redis RTT。
JWT 的优化方向 (1) 短期 access + 长期 refresh：access 15min，refresh 7d，refresh 时重查权限，实现动态权限。
(2) 密钥轮换：KID 头标识密钥版本，定期轮换。
(3) 非对称 RS256：私钥签发，公钥验签，网关只持公钥，签发服务隔离。
(4) 本地 jti 缓存：最近吊销的 jti 用进程内 LRU 兜底，减少 Redis 查询。
(5) Token 内嵌最小权限：仅放 user_id + role，详细信息查 Auth 服务。

3. Redis Lua 令牌桶 vs 滑动窗口 · 限流策略选型

网关用 Redis + Lua 脚本实现令牌桶 burst=100, sustained=10/s，对比滑动窗口与漏桶。

策略突发流量实现复杂度分布式友好适用场景
令牌桶（本实现） 允许突发（桶里有积压令牌） 中 · Redis Lua 天然支持 API 限流
漏桶（Leaky Bucket） 严格匀速，不突发 中 支持 流量整形 / MQ 入队
滑动窗口 中 高 · 需 sorted set 支持 精确限流
固定窗口 边界突刺 低 · 一计数器 支持 简单粗略

选 Redis Lua 令牌桶的好处 Pros

  • 原子性：Lua 脚本在 Redis 单线程内原子执行，无锁竞争。
  • 突发友好：桶里有积压令牌，瞬间高并发能放过，符合 API 网关场景。
  • 分布式一致：多网关实例共享 Redis，全局一致限流。
  • 低延迟：Redis 单次 RTT，<1ms。
  • 降级清晰：Redis 挂 → 放行（业务优先于限流）。

选 Redis Lua 令牌桶的代价 Cons

  • Redis 单点：Redis 抖动期间限流失效。
  • 用户级限流难：当前按 IP，需扩展到 user_id 维度，hash tag 拓展。
  • 无公平调度：同一 IP 多用户互相挤压。
  • 无多维度组合：不能按 user + path + method 灵活组合。
  • Lua 脚本维护：升级需 EVALSHA + 兼容版本。
限流的优化方向 (1) 多维度：user_id + path + method 组合 key，精细限流。
(2) 本地兜底：golang.org/x/time/rate 进程内 token bucket，Redis 故障时本地兜底。
(3) 分层限流：网关层粗限（IP），服务层细限（user + path），双层防护。
(4) 熔断器：失败率超阈值 → 暂停该 user/path 转发，半开探测恢复。
(5) Adaptive Limiter：基于后端 RTT / CPU 自适应调限流阈值，Netflix style。
(6) Redis Cluster：把限流 key hash 分片，避免单 Redis 瓶颈。

4. 洋葱中间件 vs Filter Chain · 为什么选洋葱

Gin 用洋葱模型（c.Next() 递归 + defer 倒序回弹），对比 Java Filter Chain 与 Spring Interceptor。

洋葱中间件的好处 Pros

  • before/after 对称：同一中间件可同时写 before 与 after 逻辑，无需分离。
  • 同 goroutine：全程一个 goroutine，RequestID 等上下文天然传递。
  • 异常传播正常：panic 由内层抛，外层 defer recover 接。
  • 实现简单：gin 中间件即 func(c *gin.Context)，~10 行模板。
  • 顺序直观：注册顺序即包裹顺序，看 main 就懂。

洋葱中间件的代价 Cons

  • goroutine 栈占用：每嵌套层增加栈深度。
  • 无法并行：所有中间件串行，无法并行加速（一般也不需要）。
  • 调试难：panic 栈深，不易看出哪层挂了。
  • 不能跳过：中间件需显式 c.Abort()，否则继续。
  • after 顺序易错：需理解 defer 机制。

5. RBAC vs ACL · 权限模型选型

网关用 RBAC（基于角色），权限 resource:action，对比 ACL（直接 user-permission 映射）。

维度RBAC（本实现）ACLABAC
授权单位 角色（admin/writer/reader） 用户 属性（user/resource/env）
管理成本 低 · 改角色即改全部用户 高 · 每用户单独授权 中
细粒度 中 · 角色级 高 · 用户级 极高 · 属性级
性能 查表 O(1) 查表 O(1) 需规则引擎
典型场景 企业应用 文件系统 合规审计

选 RBAC 的好处 Pros

  • 角色管理简单：3 角色 × 9 权限，一张表搞定。
  • 用户变动友好：用户升职换角色即可，无需逐权限改。
  • 性能好：角色查表 O(1)，无复杂规则。
  • 可读性高：required = "kv:put" 一眼看懂。
  • 符合企业实践：大多数业务系统都用 RBAC。

选 RBAC 的代价 Cons

  • 角色爆炸：复杂业务可能衍生几十种角色，难管理。
  • 无细粒度：无法限制「user A 只能写 collection X」。
  • 动态权限难：JWT role 一旦签发不可改，需 refresh。
  • 无多租户：当前无 tenant 维度。
RBAC 的优化方向 (1) RBAC + 数据范围：增加 scope 维度，限制 user 可访问的 collection。
(2) 多租户：JWT 加 tenant_id，权限矩阵分租户。
(3) 动态权限：token 短期 + refresh 时查 Auth 服务最新权限。
(4) ABAC 扩展：对合规场景加属性规则引擎（OPA / Cedar）。
(5) 权限缓存：网关缓存 user-permission 短期 TTL，减少 Auth 服务压力。

整体结论 · 为什么选 Go + Gin 自研网关 目标场景是「面试项目 + 中间件实践 + 业务编排」：
  • 洋葱模型清晰：能讲清中间件执行顺序，是 Go 后端面试经典题。
  • JWT + RBAC + Redis：覆盖主流后端认证体系。
  • 降级哲学：Redis 故障不阻断业务，体现工程思维。
  • 实现可控：~1500 行 Go 代码完成完整网关，复杂度合适。
代价是无动态路由 / 无服务发现 / 性能不如 nginx 系——这些是用「自研教学 + Go 易读」换来的取舍。

7. 设计原则总结

原则 1洋葱 before/after 对称

同一中间件同时处理请求前后逻辑，逻辑集中可读。

原则 2JWT 自验证 + Redis 降级

HMAC 本地验签无网络往返，Redis 抖动不阻断业务。

原则 3Recover 兜底 panic

所有 panic 由 Recover 接住，进程不崩，单请求 500 不影响其他。

原则 4幂等才重试

GET 自动重试，写操作不重试，避免重复写入。

原则 5身份透传头

网关解 JWT 后注入 X-User-ID / X-Role 给后端，后端无需再解。

原则 6优雅停机

SIGTERM → 拒新连接 → 等已有处理完，无中断退出。

原则 7RequestID 贯穿

全链路同一 ID，串联日志与追踪，故障排查必需。

原则 8降级哲学

Redis 故障时宁可放过不可错杀，业务优先于限流与安全。

Gin 网关实现边界（如实告知） 本实现是教学级网关，相比 Kong / APISIX 仍有差距：
(1) 无动态路由（改路由需重启）；
(2) 无服务发现（仅环境变量）；
(3) 无完整熔断器（只有上游失败 502）；
(4) 无可观测性内置（access_log / metrics / tracing 都需另加）；
(5) 无多租户 / 数据范围控制；
(6) 限流仅按 IP，无 user/path 维度组合。
这些都是教学版与产品级网关的关键差距，也是本页面设计分析的优化方向所在。
