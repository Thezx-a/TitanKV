前端请求链路 · 从浏览器到后端

1

用户访问 /dashboard/* browser

浏览器请求 Next.js 路由，先过 middleware.ts 校验 titan_token cookie。

崩溃点 A：无 cookie / token 失效 → middleware 重定向到 /login。

2

RSC 渲染 + apiFetch 调用 app/*

React Server Component 渲染页面，客户端用 apiFetch 或 TanStack Query 调后端 API。

崩溃点 B：后端 5xx → apiFetch 抛 HttpError，TanStack Query 捕获并展示错误 toast。

3

apiFetch · 自动注入 Bearer lib/api.ts

读 titan_token cookie → 注入 Authorization: Bearer → fetch 后端 Gateway。

崩溃点 C：401 → 清 cookie + 跳 /login（仅浏览器端，不在登录页时）。

4

TanStack Query · 数据获取与缓存 components/providers

声明式 useQuery / useMutation，自动缓存 + 失效重取 + 乐观更新。

崩溃点 D：请求失败 → TanStack 自动重试 3 次（默认），仍失败则展示错误状态。

5

RAG chat · SSE 流式渲染 lib/rag.ts

用户提交问题 → 后端 LLM 逐 token 返回 → 前端 EventSource 解析 → 累加渲染到对话框。

崩溃点 E：SSE 流中途断 → 已渲染部分保留，前端提示"中断"，用户可重新提问。

6

live-metrics · 实时指标 components/live-metrics

仪表盘首页用 SSE 或轮询展示实时指标（QPS / 延迟 / 错误率）。

崩溃点 F：指标流断 → 回退到轮询模式，UI 提示"实时数据暂停"。

核心知识点

apiFetch · 统一请求封装

web/lib/api.ts

所有后端请求都走 apiFetch，集中处理鉴权、错误、401 跳登录。

  • API_BASE：从 NEXT_PUBLIC_API_BASE 注入浏览器端，默认 http://localhost:8080。
  • 自动 Bearer：浏览器读 titan_token cookie，自动注入 Authorization: Bearer <token>。
  • query 拼接：withQuery() 用 URLSearchParams 把 query 对象拼到 URL。
  • JSON 自动解析：按 content-type 判断是否 JSON；204 返回 undefined。
  • HttpError：业务错误类，承载 status / code / message / details。
  • 401 处理：清 cookie + 跳 /login（仅浏览器端，当前不在登录页时）。
  • 便捷方法：api.get / post / put / delete。
  • credentials: include：跨域时携带 cookie。

middleware.ts · 路由级鉴权

web/middleware.ts

Next.js middleware 在请求到达页面前校验 titan_token cookie，无 token 重定向到 /login。保护 /dashboard/*。

login · 登录写 cookie

web/app/login/page.tsx

表单提交 → 调 /api/auth/login → 把 JWT 写入 titan_token cookie → 跳 dashboard。

dashboard/layout · 左导航布局

web/app/dashboard/layout.tsx

所有 dashboard 子页共享布局：左侧 nav.tsx 导航 + 右侧内容区。

rag.ts · SSE 流式问答

web/lib/rag.ts · [col]/chat/page.tsx

RAG chat 走 Server-Sent Events：后端流式输出 token，前端逐字渲染。rag.ts 封装 SSE 客户端。

  • metrics-card.tsx：单指标卡片。

  • providers.tsx：全局 Provider（TanStack QueryClient 等）。

Dashboard 各页

web/app/dashboard/
  • cluster/page.tsx：集群节点拓扑展示。
  • collections/page.tsx：Collection 列表与管理。

设计深度分析

前端控制台是用户最直接感知的层。本节覆盖崩溃恢复、Next.js App Router vs Pages Router、TanStack Query vs SWR、SSE vs WebSocket、cookie vs localStorage 等核心议题。

1. 崩溃恢复 · 六种前端场景

CASE Amiddleware 拦截未认证

用户未登录访问 /dashboard/*，middleware 重定向到 /login。用户体验稍差但安全。

语义：强制重新登录
CASE B后端 5xx 错误

apiFetch 抛 HttpError，TanStack Query 捕获并展示错误 toast；用户可手动重试。

语义：可重试 · 用户感知到错误
CASE CJWT 过期 401

apiFetch 检测 401 → 清 cookie + 跳 /login。用户重新登录后回到原页面（可加 redirect 参数）。

语义：可恢复 · 重新认证
CASE DTanStack Query 重试

请求失败默认重试 3 次，瞬时故障对用户无感；仍失败则展示错误 UI。

语义：可恢复 · 自动兜底
CASE ERAG SSE 流中断

流式响应中途断开，已渲染部分保留，前端提示"中断"。用户可重新提问（chat 是新会话）。

语义：部分结果 · 可重试
CASE F实时指标流断

SSE 流断开 → 回退到轮询模式，UI 提示"实时数据暂停"。指标数据不会全丢。

语义：可降级 · 轮询兜底
为什么这样设计？ 核心权衡：前端是用户感知层，所有崩溃必须有视觉反馈而非静默失败。错误 toast + 重试 + 重定向登录是黄金组合。代价是：用户在故障期间会频繁看到错误提示，体验降级。

2. Next.js 14 App Router vs Pages Router · 为什么选 App Router

维度App Router (本项目)Pages Router
路由 文件系统 + layout 嵌套 扁平 _app/_document
渲染 RSC + Client 混合， streaming SSR / SSG / CSR，无 streaming
数据获取 Server Component 直接 fetch getServerSideProps / getStaticProps
布局复用 layout.tsx 嵌套不重渲染 _app 全局重渲染
学习成本 RSC 概念新，需理解 Server/Client 边界 简单直观
生态成熟度 14 后稳定，部分库未适配 多年沉淀，全生态支持

结论：App Router 是 Next.js 未来方向，layout 嵌套不重渲染对管理控制台场景特别友好（侧边栏固定）。学习成本可接受。

3. TanStack Query vs SWR vs 原生 fetch · 数据层选型

维度TanStack Query (本项目)SWR原生 fetch
缓存 queryKey + 失效控制精细 key-based，简单 无
乐观更新 onMutate 回调，强 mutate 简单 无
DevTools 官方 DevTools，可视化 第三方 无
无限查询 useInfiniteQuery 原生 useSWRInfinite 需手写
包大小 ~13KB ~4KB 0
学习成本 API 丰富，需学 极简 零

结论：TanStack Query 功能最全，管理控制台场景需要乐观更新 + 无限查询 + DevTools，包大小可接受。SWR 适合轻量场景，原生 fetch 适合无状态请求。

4. SSE 流式 vs WebSocket · 为什么 RAG chat 用 SSE

维度SSE (本项目 RAG chat)WebSocket
通信方向 服务端→客户端单向 双向
协议 HTTP/1.1，自动重连 需 Upgrade 握手
代理友好 普通 HTTP 透传 需支持 Upgrade
断线重连 EventSource 内置 需手写
典型场景 LLM 流式输出、通知推送 聊天、协同编辑
连接数上限 HTTP/1.1 同域 6 个 无限制

结论：RAG chat 是单向流式输出（LLM → 用户），SSE 协议简单 + 自动重连 + 代理友好。双向聊天才需 WebSocket。

5. cookie httpOnly vs localStorage · 为什么 JWT 存 cookie

维度httpOnly cookie (本项目)localStorage
XSS 偷 token JS 读不到 localStorage.getItem 可读
CSRF 需 SameSite 缓解 不带 cookie，免疫
自动携带 同源自动带 需手动注入 header
跨域 需 credentials: include + CORS 无跨域限制
容量 4KB 5MB+
过期控制 max-age 自动 需手写定时清理

结论：httpOnly cookie 防 XSS 偷 token，是最安全默认。CSRF 用 SameSite=Strict 缓解。同源场景 cookie 是最佳选择。

6. middleware.ts vs 客户端鉴权 · 为什么在路由层校验

维度middleware.ts (本项目)客户端 useEffect 校验
执行时机 请求到达页面前 页面渲染后才校验
跳转体验 无闪烁，直接重定向 白屏后跳转，闪烁
安全 服务端校验，无法绕过 客户端可被篡改
性能 每个请求过 middleware 仅客户端执行
能力 Edge runtime，受限 API 完整 React 生态

结论：middleware 在路由层校验 cookie，无闪烁 + 不可绕过。Edge runtime API 受限但够用（读 cookie + 重定向）。客户端鉴权可作为补充（页面内权限判断）。

7. 总体优缺点与优化路线

当前设计优点

  • Next.js 14 App Router 是最新方向，layout 嵌套不重渲染
  • apiFetch 统一封装，鉴权 + 错误处理集中
  • TanStack Query 缓存 + 重试 + 乐观更新，开发体验好
  • SSE 流式 RAG chat，体验流畅
  • cookie httpOnly + middleware，安全默认

当前设计缺点

  • 无 SSR 数据预取，首屏白屏
  • 无 PWA / 离线能力
  • 无 i18n 国际化
  • 无 E2E 测试（Playwright）
  • TanStack Query 重试无指数退避
优化路线（按优先级） P0 · SSR 数据预取：Server Component 直接 fetch，首屏不白屏；
P1 · TanStack Query 指数退避：避免重试雪崩；
P1 · PWA + Service Worker：离线访问 + 推送通知；
P2 · i18n：next-intl 多语言支持；
P2 · Playwright E2E：关键流程自动化测试；
P3 · React Server Actions：替代部分 API 调用，减少客户端 JS。
为什么这个层是 L8？ L8 前端 → L1 客户端 → L2 网络库 → ... → L7 可观测性。前端层在最末端，是人类感知系统的窗口。它关键约束是：所有崩溃必须有视觉反馈，所有数据必须有缓存与重试。它通过 Gateway 调用后端，不感知分布式与存储细节。详见 客户端设计分析 与 网关设计分析。
