总览/可观测性

Observability · 横切所有层

可观测性栈不是独立的一层，而是横切所有层：每个服务暴露 /metrics 给 Prometheus 抓取， Grafana 做可视化，Jaeger 做分布式追踪，Redis 兼任限流与 jti 黑名单。一键 make docker-up 拉起。

Prometheus Grafana :3001 Jaeger :16686 Redis /metrics 分布式追踪

可观测性三支柱 · 横切调用流程

1

RequestID 生成 gateway/request_id.go

网关洋葱链第一层生成 uuid，写入 X-Request-ID 头 + c.Set("request_id")，串联后续日志与 Jaeger trace。

崩溃点 A：网关未生成 RequestID → 后端无法串联日志；可在后端 fallback 自生成。

2

指标埋点 · GinMiddleware pkg/metrics

每个 Go 服务挂 metrics.GinMiddleware("svc")，自动记录请求计数 / 延迟分布，写到本地 prometheus registry。

崩溃点 B：埋点失败（registry 满）→ 中间件吞错继续处理，不影响业务。

3

/metrics 暴露 metrics.go

服务在 /metrics 路由暴露 prometheus exposition format，等 Prometheus scrape。

崩溃点 C：/metrics 端点未挂或服务崩 → Prometheus 抓取失败，UI 显示空；不影响业务请求。

4

Prometheus 抓取 prometheus.yml

Prometheus 按 scrape_configs 周期（默认 15s）拉取所有服务的 /metrics，存入本地 TSDB。

崩溃点 D：抓取超时或 4xx/5xx → Prometheus 标记 target down，告警触发；存量指标不丢。

5

Jaeger trace 透传 middleware

RequestID 作为 trace_id 透传到下游服务，每个微服务在出站请求注入 trace header，Jaeger 自动关联成调用链。

崩溃点 E：下游未透传 trace → 链路断裂，Jaeger 显示不完整；不影响业务。

6

Grafana 可视化 :3001

以 Prometheus 为数据源，构建 QPS / 延迟分位 / 错误率 / 业务规模等仪表盘。

崩溃点 F：Grafana 不可达 → 仅影响人看图，不影响系统运行。

7

Redis · 限流 + jti 黑名单 :6379

令牌桶限流 + JWT jti 黑名单，Redis 故障时降级（限流放开 / 黑名单忽略）保证业务可用。

崩溃点 G：Redis 挂 → 限流降级为无限制，黑名单失效（已登出 token 暂时可用）；需监控 + 快速恢复。

核心组件知识点

Prometheus · 指标抓取

deploy/dev/prometheus.yml · services/observability/metrics.go
  • 抓取目标：各服务的 /metrics 端点，prometheus.yml 配置 scrape_configs。
  • 指标暴露：Go 服务用 prometheus client，services/observability/metrics.go 定义业务指标。
  • HTTP 中间件：pkg/metrics.GinMiddleware("gateway") 自动记录请求计数 / 延迟分布。
  • 注册路由：metrics.RegisterRoutes(r) 暴露 /metrics 给 Prometheus。

Grafana · 可视化仪表盘

deploy/dev/docker-compose.yml

以 Prometheus 为数据源，构建请求 QPS / 延迟分位 / 错误率 / 业务规模等仪表盘。默认 http://localhost:3001。

Jaeger · 分布式链路追踪

deploy/dev/docker-compose.yml · middleware/request_id.go

跨网关 → 微服务 → 存储引擎关联一次请求的全链路。X-Request-ID 由网关生成，透传给后端，Jaeger UI 默认 http://localhost:16686。

Redis · 限流 + jti 黑名单

middleware/ratelimit.go · middleware/auth.go
  • 限流：令牌桶 burst=100, sustained=10/s，Redis 故障时降级为无限制。
  • jti 黑名单：登出写入 revoked:jti:<id>，TTL = token 剩余有效期。

Observability 服务 · 聚合与采集

services/observability/
  • metrics.go：业务指标定义与暴露。
  • scraper.go：周期采集其他服务指标，聚合展示。
  • handler.go：HTTP 接口。
  • cmd/main.go：服务入口，默认 :8084。

设计深度分析

可观测性不是功能层，而是横切所有层的"神经系统"。本节覆盖崩溃恢复、Prometheus vs InfluxDB、Jaeger vs Zipkin、Redis 限流降级、采样策略等核心议题。

1. 崩溃恢复 · 七种场景

CASE ARequestID 缺失

后端 fallback 自生成 uuid，仅丢失跨服务串联能力。业务请求正常处理。

语义：可降级 · 追踪能力降级
CASE B指标埋点失败

中间件吞错继续处理，不影响业务请求。Grafana 上对应指标短暂缺失。

语义：可降级 · 仅监控盲区
CASE C/metrics 端点不可达

Prometheus 抓取失败，UI 显示 target down。存量指标不丢，告警触发。

语义：监控盲区 · 不影响业务
CASE DPrometheus 抓取超时

网络抖动或服务慢，Prometheus 标记 target down 但不丢存量数据。15s 后下次抓取恢复。

语义：可恢复 · 短暂盲区
CASE Etrace 透传断裂

下游未透传 trace header，Jaeger 链路不完整，但业务请求正常。

语义：可降级 · 链路追踪能力降级
CASE FGrafana 不可达

仅影响人看仪表盘，不影响系统运行。数据仍在 Prometheus 里。

语义：无损 · 仅 UI 不可见
CASE GRedis 故障

限流降级为无限制（防误杀业务），jti 黑名单失效（已登出 token 暂时可用）。需快速恢复 + 监控告警。

语义：安全降级 · 攻击窗口扩大
为什么这样设计？ 核心权衡：可观测性栈的故障绝不能影响业务。所有埋点、抓取、可视化都设计成"失败降级"而非"失败阻塞"——Redis 挂时限流放开而非拒绝请求，Prometheus 挂时只影响看图不影响请求。代价是：故障期间监控盲区 + 安全降级窗口。

2. Prometheus vs InfluxDB vs OpenTSDB · 指标库选型

维度Prometheus (本项目)InfluxDBOpenTSDB
数据模型 多维 label，pull 模型 tag + field，push 模型 tag + value，push 模型
查询语言 PromQL，简洁强大 Flux / InfluxQL，复杂 类 SQL，简单但功能少
抓取方式 主动 pull，对服务无压力 被动 push，需 agent 被动 push，需 agent
生态 CNCF 标准，Grafana 一键集成 自有可视化工具 Hadoop 生态，老旧
长期存储 需 Thanus / Cortex 扩展 原生支持 原生支持 HBase

结论：Prometheus 是 CNCF 事实标准，Pull 模型对服务无侵入，PromQL 表达力强，Grafana 集成最佳。长期存储需 Thanus 扩展，但本项目数据量小暂不需要。

3. Jaeger vs Zipkin vs SkyWalking · 链路追踪选型

维度Jaeger (本项目)ZipkinSkyWalking
协议 OpenTelemetry 标准 自有 B3 协议 自有协议
侵入性 SDK + OpenTelemetry SDK 字节码增强，零侵入
生态 CNCF 标准 Spring 生态强 Apache 项目，中文友好
性能 高，采样可调 中 高，但 JVM agent 重
UI 调用链 + 拓扑图 调用链为主 拓扑 + 调用链 + 指标

结论：Jaeger 是 CNCF 通用标准，与 OpenTelemetry 兼容，未来切换 SDK 不绑死。SkyWalking 字节码增强适合 Java 项目，本项目是 Go + C++，Jaeger 更合适。

4. Redis 限流 · 为什么用令牌桶不用漏桶

维度令牌桶 (本项目)漏桶
突发流量 允许 burst（桶满） 严格匀速，无突发
实现 Lua 脚本 + INCRBY + EXPIRE 需队列或令牌池
典型场景 API 网关，允许短暂突发 消息队列消费端
失败降级 Redis 挂时放开限流 需双写或主备

结论：API 网关场景下用户请求有自然突发（点击 + 重试），令牌桶允许 burst 更友好。漏桶适合下游严格匀速的场景。

5. Redis 限流降级 · 为什么不直接拒绝请求

降级放开的优点

  • Redis 故障不阻塞业务，可用性优先
  • 避免 Redis 故障导致全站 503
  • 快速恢复后限流自动生效

降级放开的代价

  • 故障期间可能被 DDoS 打穿
  • jti 黑名单失效，已登出 token 可用
  • 需配合其他防护（WAF / IP 限速）

优化方向：① Redis 主从 + Sentinel 高可用；② 限流双轨：Redis 在线用 Redis，故障时切到本地内存令牌桶（粗粒度兜底）；③ jti 黑名单加本地缓存 + 定期同步，故障时仍能用旧快照挡一部分。

6. 采样策略 · 全量 vs 采样

维度全量 (本项目)头部采样尾部采样
实现 无需采样逻辑 入口按比例决定 出口按错误率动态
存储成本 高，QPS 大时不可行 低，固定比例 中，错误全留 + 正常采样
调试友好 所有请求都能查到 大多数请求查不到 错误请求都查到
适用规模 教学 < 1k QPS 中大规模 大规模生产

结论：教学场景全量保留方便调试；生产场景建议尾部采样（错误全留 + 正常 1% 采样），既省存储又能查错误。

7. 结构化日志 vs 文本日志

维度结构化 JSON (本项目)纯文本
查询 字段过滤，高效 正则匹配，慢
聚合 按字段 group 需先解析
可读性 需工具渲染 直接可读
存储 略大（字段名重复） 紧凑

结论：结构化日志便于 ELK / Loki 聚合查询，生产场景必选。开发期可用 jq 渲染提升可读性。

8. 总体优缺点与优化路线

当前设计优点

  • 三支柱齐全：Metrics + Tracing + Logging
  • Prometheus + Jaeger + Grafana 是 CNCF 黄金组合
  • RequestID 贯穿所有层，串联日志 + trace
  • Redis 故障降级而非阻塞业务
  • 一键 make docker-up 拉起完整栈

当前设计缺点

  • 无长期存储（Prometheus 本地 TSDB 15d）
  • 无采样策略，QPS 大时存储爆炸
  • Redis 降级期间 jti 黑名单失效
  • 无 alertmanager 告警通道
  • 结构化日志未接入 Loki / ELK
优化路线（按优先级） P0 · alertmanager + 告警规则：Prometheus 触发后路由到邮件 / 钉钉；
P1 · Loki + 结构化日志聚合：统一查询 Metrics + Logs；
P1 · 尾部采样：错误全留 + 正常采样，省存储；
P2 · Thanus 长期存储：Prometheus 数据上 S3，长期保留；
P2 · Redis 主从 + Sentinel：提升限流可用性；
P3 · OpenTelemetry 统一 SDK：消除 Jaeger 自有 SDK 绑定。
为什么这个层是 L7？横切所有层 L7 不在垂直调用链上，而是横切 L1~L8 所有层。每个服务都暴露 /metrics，每个请求都带 RequestID。这样设计的好处是：观测能力对所有层统一，新加服务只需挂中间件即接入观测网。详见 网关设计分析 与 微服务设计分析。
